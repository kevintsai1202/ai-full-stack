## 這句話的問題是：沒有基準

❌「幫我看看有沒有資安漏洞」

沒有基準，AI 只會回你泛泛而談的三五點：「注意 SQL injection、記得驗證輸入、密碼要加密」。聽起來都對，但你不知道它**漏了什麼**。

給它一份清單，它就變成逐項稽核，而且**有覆蓋率可以談**。這裡分兩層：**你寫的程式碼**，和**你拉進來的東西**。

## 第一層：我寫的程式碼——對照 OWASP 與 CWE

### 提示詞全文（可直接複製）

```text
對照 OWASP Top 10:2025 與 CWE Top 25（2025 版）逐項檢查這份程式碼，
輸出表格：分類代號、是否命中、程式位置、風險等級、修補建議。
沒命中的項目也要列出，並說明為什麼不適用。
```

關鍵在最後一句：「**沒命中的項目也要列出，並說明為什麼不適用。**」這一句是逼它交出覆蓋率。只列命中項目的報告，你根本無法判斷它是查得仔細，還是只挑了幾個好講的講。

而且請注意**清單版本**。OWASP Top 10 在 2025 年 11 月發表新版、2026 年 1 月定版，新增了兩個分類：**A03 軟體供應鏈失效**、**A10 例外狀況處理不當**，SSRF 則被併進 A01。如果你拿 2021 年的舊清單去問，你會整整漏掉供應鏈跟例外處理這兩塊。

實際跑出來的稽核摘要：

![稽核摘要表：命中 4 項 OWASP、1 項 CWE，未命中項目也逐一列出不適用原因](https://springai-media.zeabur.app/newsletter-media/images/2ece06469ac938549b69587ace3e059dbd7b8b2c6fe4de0fcc2514286bfa67ac.png)

命中 4 項 OWASP、1 項 CWE——**不是全綠**。這很重要：全綠的稽核報告通常代表查得不夠仔細。

其中 A10（例外狀況處理不當）這項不是「可能有風險」，是實際驗證出來的：我故意把資料檔弄壞，然後打 API——它回了 500，而回應裡帶著我的檔案系統路徑。

## 第二層：我用的第三方元件——已知 CVE

自己寫的程式碼是一回事，你拉進來的東西是另一回事。

### 提示詞全文（可直接複製）

```text
列出本專案所有相依套件與版本，逐一查有無已知 CVE，
標出 CVSS 分數、影響說明與建議升級版本，依風險排序。
```

我的示範專案 `npm audit` 是乾淨的，0 個已知漏洞。但重點在下一行：**5 個直接相依，帶進了 106 個套件**。

![相依套件稽核：npm audit 回報 0 漏洞，但 5 個直接相依實際帶進 106 個套件](https://springai-media.zeabur.app/newsletter-media/images/a3269b804c150b24c8ef441748e4e388d0852bdef10c39fe4587316957e6808e.png)

0 漏洞的意思是「**今天**乾淨」。沒有任何機制會在明天有新漏洞的時候通知你——這正好對應 2025 新版特地加進來的 A03 軟體供應鏈失效。定期重跑這一層，或在 CI 裡掛上自動掃描，才算把「今天」變成「每天」。

## 修掉之後：資訊不是消失，是換了去處

稽核出來的問題修掉之後，對比長這樣：

![修補前後對比：修補後用戶端只收到制式的「伺服器內部錯誤」，完整錯誤與路徑進了伺服器日誌](https://springai-media.zeabur.app/newsletter-media/images/eb37916f33037ee698dc42a4d97ea5c1b7778ef43596d4be76d7d22b53ab2078.png)

修補後，用戶端只會收到「伺服器內部錯誤」，而完整的錯誤——包含路徑跟 stack——進了日誌。**資訊不是消失，是換了去處。**

順帶一提，這也是為什麼「開啟日誌」必須先做：把錯誤從回應裡拿掉卻不記錄，等於把問題變成靜默失敗——你只是把洩漏改成了失明。

## 一句誠實話

AI 稽核**取代不了滲透測試**。它沒有實際嘗試組合攻擊路徑、沒有測競爭條件、沒有驗證商業邏輯能不能被繞過。

它的價值是**便宜的第一道網**——在你花錢請人測之前，先把明顯的東西掃掉。

稽核全綠不等於安全。只等於「清單上的項目都看過了」。

四站走完，收成一張表——這張可以存：

| 階段 | ❌ 別這樣問 | ✅ 這樣問 | 你會拿到的產物 |
|---|---|---|---|
| 想法期 | 這個能不能做？ | 做一份可行性評估報告，含難易度分級、風險、驗證順序 | 可進會議、可被打槍的評估文件 |
| 設計期 | 幫我寫一個 X | 先選型分析 → 再開發計畫 → 才實作 | 選型比較表＋里程碑與驗收標準 |
| 開發驗收 | 幫我測試有沒有問題 | TDD 紅綠重構 → Playwright 腳本 → 截圖生 SOP | 回歸測試資產＋操作手冊 |
| 上線前 | 幫我看有沒有漏洞 | 對照 OWASP／CWE 逐項稽核，含未命中原因 | 有覆蓋率的稽核表 |

這四招的共通點只有一個：**你要求了一份別人可以審查的東西。**

可行性評估報告可以被打槍、開發計畫可以被改、測試會紅、稽核表有覆蓋率。這四樣東西都可以被審查——而「可以做」不行。

把「一句話回答」換成「可審查產物」。就這一句。

系列完結，感謝收看。下次開口問 AI 之前，先想一下：我要的是一句話，還是一份文件？

# 主題二｜事件收得下來：重複執行的代價

上期用 Outbox 把事件變成一筆資料，確保它不會在交易失敗時亂送、也不會在當機時消失。

但 Outbox 帶來了下一個問題。排程的流程是這樣的：

1. 撈出還沒送出的事件
2. 送出去
3. 標記「已送出」

如果在第 2 步和第 3 步**之間**當機——事件已經送出去了，但資料庫還記著「這筆還沒送」。重開之後，排程會再送一次。

這不是 Outbox 特有的毛病。訊息佇列、webhook、任何跨程序的傳遞都一樣，因為要真正做到「剛好一次」，送出方和接收方得在同一個交易裡，而它們在不同的機器上。

所以整個業界的共識是：**先保證「至少一次」，剩下的交給接收端自己處理重複。**

![事件重送的成因：排程送出事件分成「① 撈出未送出的 → ② 送出去 → ③ 標記已送出」三步，若在 ② 和 ③ 之間當機，第三步沒跑到；重開之後資料庫還記著「這筆沒送」，於是又撈到同一筆、再送一次，下游收到第二次](https://springai-media.zeabur.app/newsletter-media/images/e1c59207c014b71efcc7642f039cb453510a70febec4947baa81a2b62b8d3629.png)

上期講 Webhook 的時候我引過一句話：那四道關卡，本質是在 HTTP 上手工補回訊息佇列原生提供的保證。這期要補的就是其中最關鍵的一道——**去重**。

## 一般系統重跑沒事，Agent 重跑要命

在一般的 CRUD 系統裡，重複處理通常是無害的。重新計算一次訂單總額，答案還是同一個；重新更新一次狀態，結果也一樣。

Agent 不是。我實際跑了一次「沒有任何保護、同一個事件送兩次」：

```text
I1 沒有保護時，同一事件送兩次就呼叫兩次 LLM
   LLM 呼叫次數=2
```

兩次呼叫代表：

- **付兩次錢**——按 token 計費，跑幾次算幾次
- **拿到兩份不一樣的摘要**——LLM 不保證同樣輸入給同樣輸出
- **後寫入的覆蓋先寫入的**——而哪一份會贏，取決於誰先跑完，完全隨機

第三點最麻煩：這不是「多花一點錢」的效率問題，而是**資料變得不可預測**。同一筆客戶資料，重整頁面前後看到不同的摘要，而你查不出為什麼。

## 後段：冪等鍵，以及一個不能顛倒的順序

### 冪等鍵要用什麼

先講一個常見的錯誤：**用 `customerId` 當去重的依據**。

那會變成「同一個客戶永遠只產生一次摘要」——但客戶資料改了本來就該重新產生摘要。你要擋的是「同一次更新被處理兩次」，不是「同一個客戶被處理兩次」。

正確的做法是讓**每一個事件有自己的識別碼**，在事件產生的當下就決定好：

```java
/** 事件帶自己的識別碼，在產生的當下決定，重送時不會變 */
public record CustomerUpdated(String eventId, Long customerId) {}
```

如果用的是上期的 Outbox，那 outbox 表的主鍵就是現成的 `eventId`——重送的是同一筆資料，識別碼自然一樣。

### 順序不能顛倒

接下來是這期真正的重點。你需要一張表記住「哪些事件處理過了」：

```sql
create table processed_events (
    event_id varchar(64) primary key   -- 主鍵，不是普通欄位
);
```

處理事件的時候，**先卡鍵，再做事**：

```java
@Async
@TransactionalEventListener
public void on(CustomerUpdated event) {
    try {
        // 先搶下這個事件的處理權——搶不到就代表別人已經在做了
        jdbc.update("insert into processed_events(event_id) values (?)", event.eventId());
    } catch (DuplicateKeyException alreadyHandled) {
        return;   // 安靜跳過，這不是錯誤
    }

    // 搶到了才呼叫 LLM
    aiSummaryService.regenerate(event.customerId());
}
```

實測，送兩次：

```text
I2 先卡冪等鍵：送兩次只呼叫一次 LLM
   LLM 呼叫次數=1
```

單執行緒會過不稀奇。真正的考驗是並行——十條執行緒同時搶同一個事件：

```text
I3 10 條執行緒同時搶同一事件，LLM 仍只被呼叫一次
   LLM 呼叫次數=1
```

十搶一，只有一條做事。

### 反過來寫，保護就完全失效

很多人會直覺地寫成這樣——先查查看處理過沒有，沒有才做：

```java
// ⚠️ 這是反例，不要照抄
Integer seen = jdbc.queryForObject(
        "select count(*) from processed_events where event_id = ?", Integer.class, eventId);
if (seen != null && seen > 0) return;

aiSummaryService.regenerate(customerId);   // 呼叫 LLM

jdbc.update("insert into processed_events(event_id) values (?)", eventId);
```

看起來也擋得住，單執行緒測起來甚至會過。但同樣十條執行緒並行：

```text
I4 反例——先查再做，並行下擋不住
   LLM 呼叫次數=10（10 條執行緒中有這麼多條同時通過了檢查）
```

**十條全部通過檢查、十條全部呼叫了 LLM。** 保護等於不存在。

![同樣 10 條執行緒搶同一個事件的兩種寫法對比：左邊「先卡鍵」用 insert 冪等鍵讓資料庫的主鍵約束擋下，檢查與佔位是同一個原子操作，只有 1 條通過，實測 LLM 呼叫次數＝1；右邊「先查再做」用 select 查處理過沒有，查與寫之間的空隙裡十條全都查到還沒處理，10 條全過，實測 LLM 呼叫次數＝10](https://springai-media.zeabur.app/newsletter-media/images/7c38a8866b5bea589d33e08918b2e0d72be8deef051518670df319f3800ae181.png)

原因是「查」和「寫」之間有一段空隙。十條執行緒在那段空隙裡都查到「沒處理過」，於是十條都認為自己該做。

而 `insert` 加上主鍵約束不會有這個空隙——**檢查和佔位是資料庫在同一個原子操作裡完成的**，這是應用層的 if 判斷做不到的事。

所以這條規則可以記得很簡單：

> **不要問「處理過了嗎」，直接試著「登記我要處理」，失敗就代表別人先登記了。**

### 順手把狀態也記下來

既然都要寫一張表了，多存兩個欄位會讓後面幾期輕鬆很多：

```sql
create table processed_events (
    event_id     varchar(64) primary key,
    status       varchar(20) not null,     -- PENDING / DONE / FAILED
    attempts     int         not null default 0,
    last_error   varchar(500),
    updated_at   timestamp   not null
);
```

有了 `status`，你才有辦法回答「這筆摘要到底跑完了沒」——這正是下期要處理的問題。

🤖 檢查自己專案的重複處理風險，可以把這句丟給 AI：

```text
找出這個專案裡所有處理外部訊息或事件的進入點
（webhook 端點、訊息佇列消費者、排程撈取任務、@EventListener）。
逐一回答：
1. 這個處理如果被重複執行兩次，會發生什麼事？特別標出會付費、會發信、會寫入外部系統的。
2. 目前有沒有去重機制？如果有，是用「先查再做」還是「唯一約束擋下」？
3. 「先查再做」的位置全部列為高風險——並行時擋不住。
列成表格並依風險排序。先不要改程式碼。
```

但有件事一路上愈來愈嚴重——**使用者完全看不到這一切**。

我們把等待從使用者身上拿掉，卻也把「知道進度」一起拿掉了。下期就把它補回來。

## 1. 背景與定位

### 現況

電子報自 011 期起改為「一期兩主題」。012–015 的主題一已完成（「可審查產物」系列站 1–4，改編自直播《別再問 AI「能不能做」》），但四期的**主題二全部標註「預留、尚未定題」**。015 是可審查產物系列的完結期，016 的主題一也隨之空出。

### 定位依據

課程《AI 賦能全端開發》的 Unit 6／Unit 7 教到 Spring AI ChatClient、SSE 串流、tool calling、RAG／pgvector、MCP，**但完全未涵蓋事件驅動**。因此 EVENT 系列不是課程複習，而是課程結業後的下一步，「進階」定位成立。

### 為什麼是 AI Agent × 事件

AI Agent 具備一般 CRUD 沒有的三個特性，使同步架構的既有缺點被顯著放大：

1. **慢** — 單次 LLM 呼叫動輒數十秒
2. **貴** — 按 token 計費，重跑就是重複付費
3. **不可重複** — 同一輸入兩次執行結果未必相同

這三點讓「為什麼需要事件」不需要抽象論證，用讀者自己的 AI CRM 就能講清楚。

### 與既有內容的接點

011 期正文已寫下：「本質是在 HTTP 上手工補回訊息佇列原生提供的保證」。該句為本系列預留了入場伏筆，E3 負責回收。

### 排期的四個理由

1. **先給地圖再進細節**：沿用 008 期（即時通訊地圖）建立的成功模式，E0 先攤開事件驅動的座標，讀者才知道後續各期在整張圖的哪個位置。
2. **E0／E1 的分界落在一個認知修正點**：Spring 的 `ApplicationEventPublisher.publishEvent()` **預設為同步**，與發布端同執行緒、同交易。實務上極常被誤解為「發事件＝非同步」。因此 E0 講**解耦**（同步事件即可達成），E1 才講**非同步**（`@Async` 與其陷阱）。此分界同時讓 E0 有可實跑的程式碼，不流於純概念。
3. **分期用動詞而非技術名詞**：E1–E4 以「送得出去／收得下來／回得了前端」分期，而非 Outbox／冪等／死信。技術名詞當標題會篩掉尚未意識到自己需要它的讀者，而那正是最需要閱讀的族群。
4. **不留系列空窗**：015 完結後 016 主題一原本空出，E4 升格接手，讀者的連載慣性不中斷；E5 續接 017。

## 4. 各期內容邊界

付費牆切點統一為「為什麼」與「怎麼做」之間：前段為痛點與原理，免費讀者亦可帶走完整觀念；後段為可複製的程式碼與可直接丟給 AI 的提示詞。

### E0｜事件驅動的地圖：解耦，還不是非同步（012 主題二）

**前段**
事件驅動的座標：誰發、誰收、承諾什麼保證。以 AI CRM 為例——「客戶資料更新」這件事，目前是誰直接呼叫誰；一旦要再加「更新後產生 AI 摘要」「更新後通知業務」「更新後寫稽核紀錄」，直接呼叫會長成什麼樣子。帶出耦合的代價：每加一個下游，就要改一次上游。

同時交代與既有內容的關係：011 講的 webhook 是「跨系統」的事件，本系列講的是「同一個系統內」的事件，兩者是同一種思路的不同尺度。

**後段**
- `ApplicationEventPublisher` 最小可跑範例：把直接呼叫改成發事件
- **核心認知修正**：`publishEvent()` 預設是同步的——監聽器與發布端同執行緒、同交易，監聽器拋例外會傳回發布端。「發事件」不等於「非同步」
- 判斷清單：什麼情況適合事件化、什麼情況直接呼叫就好（避免讀者過度套用）

**結尾預告**：E1（既然預設是同步的，那 Agent 那種要跑 30 秒的工作怎麼辦）

### E1｜為什麼 Agent 一定要非同步（013 主題二）

**前段**
AI CRM 的「產生客戶摘要」同步執行的後果：使用者等待 30 秒、HTTP 逾時後前端重送、LLM 二次呼叫二次計費。據此帶出 Agent 與一般 CRUD 的三個差異（慢、貴、不可重複）。

**後段**
- `ApplicationEventPublisher` 最小可跑範例
- `@Async` 的三個常見誤用：交易語意失效、例外被吞掉、預設執行緒池設定不敷使用

**結尾預告**：E2（事件送出去之後，交易 rollback 了怎麼辦）

### E2｜事件送得出去：交易邊界與 Outbox（014 主題二）

**前段**
易錯場景：客戶資料存檔後發事件觸發 AI 摘要，交易隨後 rollback，事件卻已送出，Agent 對著不存在的資料產生摘要。

**後段**
- `@TransactionalEventListener(AFTER_COMMIT)` 實作
- 該做法擋不住的缺口：commit 完成後、事件送出前當機
- Outbox 表最小實作

**結尾預告**：E3（訊息重送在 Agent 身上的代價）

### E3｜事件收得下來：重複執行的代價（015 主題二）

**前段**
回收 011 伏筆：「至少一次送達」在一般系統只是重算一次，在 Agent 是重燒一次 token，且兩次結果未必相同。

**後段**
- 冪等鍵設計：以什麼欄位組合為 key
- 處理狀態表
- 「LLM 呼叫前先卡一道」的順序為何不可顛倒

**結尾預告**：E4（非同步之後，使用者看不到進度了）

### E4｜事件回得了前端：進度、失敗與死信（016 主題一）

**前段**
非同步化的代價是使用者失去感知，必須把感知補回來。

**後段**
- 事件 → SSE 推送進度（回收 009 期，老讀者有回收感）
- 重試與退避策略
- 死信佇列與人工介入關卡

**結尾預告**：E5（Agent 自己跑的每一步，誰來審查）

### E5｜事件即 Agent 的稽核軌跡（017 主題一）

**前段**
呼應 012–015 主軸：你要求 AI 交出可審查產物，那 Agent 自己執行的每一步呢？

**後段**
- 把提示、工具呼叫、回應、token 用量記成事件流
- 用途三支：回放、稽核、成本歸屬

## 5. 製作與驗證規範

### 5.1 程式碼驗證（強制）

沿用 `newsletter/scripts/verify-0NN-*.mjs|ps1` 慣例，每期一支留在 repo 的可重跑腳本。

**本系列特有的新問題**：驗證腳本不得真的呼叫 LLM（會產生費用，且結果不可重現）。

**做法**：以假物件替換 `ChatClient`，讓腳本驗證的對象是**事件機制本身**：

- 事件是否確實在 commit 之後才送出
- 重複事件是否被冪等鍵擋下
- 退避序列是否符合預期間隔

上述皆為純 Java 邏輯，可用 `javac -cp ~/.m2` 串接既有 jar 編譯最小骨架驗證，不需啟動完整 Spring 專案。

**環境注意**：`mvn` 需明確指定 `JAVA_HOME=/d/java/jdk-21`（shell 預設為 JDK 8）。

### 5.2 反例佐證（強制）

每期至少一組。E2 的交易 rollback、E3 的重複執行，須同時驗證「正確寫法通過」與「錯誤寫法確實出事」。錯誤寫法保留為迴歸測試，防止日後改回；同時它即是文中警語的證據。

### 5.3 素材

沿用 008–011 的 SVG → PNG 管線（`newsletter/assets/` 原始 SVG、`render-diagrams.mjs` 轉檔、`uploaded-urls.txt` 記錄 hash）。

每期 2 張圖：一張呈現「壞掉的樣子」、一張呈現「修好的結構」。E3 的圖沿用 011 那張 webhook 四道關卡的視覺語言，使讀者辨識出同一條脈絡。

## 6. 不做什麼（YAGNI）

- **不做多 Agent 事件協作（Saga／編排）**：氣勢足但讀者需先具備 E1–E4 基礎，且不易在單篇內提供可實跑的驗證程式碼。留作日後獨立系列。
- **不做 Event Sourcing／CQRS 完整論述**：屬資料建模層級，距離讀者日常較遠，與本系列「解決 Agent 實際痛點」的定位不符。
- **不比較訊息佇列產品**（Kafka vs RabbitMQ vs Redis）：選型比較是另一種文章型態，會稀釋主線。必要時僅在 E2 Outbox 一節以一段話帶過。

# teaching-site 章節知識與應用情境分析

日期：2026-08-25  
分析範圍：`teaching-site/course-data.js` 目前載入的 `u1`–`u12`、`teaching-site/AGENTS.md`、`teaching-site/CLAUDE.md` 與 `課程內容.md`  
文件狀態：僅供課程內容評估；本次不修改 teaching-site 網站、課程資料、提示詞或渲染程式

## 一、結論先行

目前每個章節都可以對應到具體的工作情境，但「學生能不能快速理解用途」的清楚程度並不一致：

- `u2`–`u7` 已經有最明確的業務連結，能直接對應客戶管理、權限、工作台、AI 助理與知識庫。
- `u1` 的技術很重要，但偏向開發者基礎設施；需要用「新同事如何在一天內把專案跑起來」來說明價值。
- `u8`–`u12` 多數是整合、交付與維運知識；學生容易只記得指令，因此必須把它們連到「交付給別人、公開展示、更新、退版、服務不中斷」等結果。
- 最適合全課共用的主線是：業務打開客戶頁面，查看真實資料，請 AI 產生摘要與下一步建議；後續再把同一套系統打包、上線、更新與擴展。

建議每章都固定回答四個問題：

1. 現在遇到什麼實際問題？
2. 這項技術負責解決哪一段問題？
3. 在 AI CRM 中會出現哪個操作畫面或 API？
4. 學生完成什麼可觀察的結果，才能確認真的理解？

## 二、分析範圍與貫穿案例

網站目前的資料結構是三個教學日、12 個單元：

| Day 1 | u1–u4 | 從環境到安全後端 | 可啟動、可持久化、可驗證、可授權的 API |

舊版 `課程內容.md` 主要描述 8 個核心單元與 1 個 Cloudflare 延伸單元；目前網站資料已進一步拆出 u10–u12。因此本文件以網站實際呈現的 12 個單元為分析基準，避免學生看到的章節與評估結果不一致。

全課可以反覆使用三家示範客戶，讓技術不變成孤立名詞：

- **亞太智能製造 APIM：高價值且活躍**。適合示範商機金額、互動頻率、推薦方案與高價值客戶經營。
- **環球零售巨擘 GlobalMart：流失風險**。適合示範最近互動、客訴、競品比較、風險提醒與優先跟進。
- **鼎峰金融科技 ApexFin：續約延遲**。適合示範資料不足、歷史互動檢索、條款查詢與人工確認下一步。

## 三、逐章分析

### u1 開發環境、專案骨架與 AI 協作流程

**傳授知識**

- Windows／macOS 開發工具基線：PowerShell 7、JDK 21、Maven、Git、Node.js、Python、VS Code。
- Spring Initializr、Maven 專案結構、`backend`／`frontend` 分離與初次啟動驗證。
- 工具責任邊界：執行環境負責跑程式，編輯器負責編輯與除錯，AI 協助解釋、產生樣板與排錯。
- AI 協作的基本流程：先說需求與限制，再產生程式，最後用實際指令驗證。

**技術用途**

這一章不是在教一串安裝指令，而是在建立可重現的開發起點。所有學生使用相同的 Java、Maven 與 Node 版本，後續遇到問題時才有可能區分「環境問題」與「程式問題」。

**具體應用情境／舉例**

1. 新同事加入 CRM 專案，依照同一份環境檢查清單安裝工具，執行 `/api/health` 後即可確認後端與前端是否能互通。
2. 學生的 Maven 使用 Java 8，但專案要求 Java 21；透過 `mvn -version` 找出 Maven 實際使用的 JDK，而不是只看 `java -version`。
3. AI 產生 Spring Boot 專案骨架後，學生要求 AI 解釋每個目錄的責任，再用 `mvn clean compile` 或啟動結果驗證，不直接把產碼當成完成。

**一句話定位**

> u1 解決的是「每個人能不能在同一個可重現的起點開始工作」。

**理解檢核與評估**

學生不只要說出工具名稱，還應能回答：如果前端能啟動但後端不能啟動，要先檢查哪個程序？如果 AI 給了看似合理的設定，要用什麼命令驗證？本章目前已有環境驗證任務，應特別強調「版本與實際執行結果」而非安裝完成畫面。

### u2 Spring MVC、REST API 與 CRM Domain Modeling

**傳授知識**

- Spring Boot 自動配置、Spring MVC 的 `DispatcherServlet` 請求流程。
- REST 資源設計、HTTP 方法、狀態碼與無狀態請求。
- `Controller → Service` 分層，並為後續 `Repository → Database` 做準備。
- DTO、Lombok、Bean Validation 與一致的 400／404 回應。
- CRM 核心領域：Customer、Contact、Opportunity、Activity／Interaction、Task。

**技術用途**

這一章把「業務需求」翻譯成前端可以呼叫的 API。分層讓 HTTP 格式、商業規則與資料來源各自有責任；Validation 則避免錯誤資料一路進入系統。

**具體應用情境／舉例**

1. 業務在客戶頁面新增一筆互動紀錄：前端送出 `POST /api/customers/{id}/interactions`，Controller 解析請求，Service 判斷客戶是否存在與紀錄是否合理，再回傳 201。
2. 客戶名稱為空或 Email 格式錯誤時，API 回傳 400 與欄位錯誤；學生可以用 PowerShell `Invoke-RestMethod` 重現錯誤，理解為什麼不能相信前端輸入。
3. 查詢不存在的客戶時回傳 404，而不是回傳空物件或 200；這個差異能直接影響前端要顯示「找不到客戶」還是「資料載入成功」。
4. 後續把資料從 Java `List` 換成 JPA Repository 時，Controller 不需要知道資料來源改變，學生能看到分層設計的實際收益。

**一句話定位**

> u2 解決的是「使用者的一個操作，如何變成清楚、可預期、可維護的 API」。

**理解檢核與評估**

最適合用一條完整請求追蹤來驗收：`POST 新增客戶 → Validation → Service → 回應 JSON`。目前章節概念很完整，建議評估時要求學生自行說明每一層如果放錯邏輯，未來會造成什麼維護成本。

### u3 PostgreSQL、Flyway、JPA 與動態查詢

**傳授知識**

- Docker 容器化 PostgreSQL 與 pgvector，讓開發環境可快速建立與重置。
- Flyway migration、版本命名、雙底線規則與 schema 可追溯性。
- `application.yml` 資料庫設定與連線。
- JPA Entity、關聯映射、Repository、Query Method、Lombok 與 Audit 欄位。
- `@Transactional`、`@Modifying`、Lazy Load、N+1 查詢風險。
- Specification 與多條件動態查詢的選用時機。

**技術用途**

資料庫解決「應用程式重啟後資料仍在」的問題；Flyway 解決「資料表怎麼演進且每個環境一致」的問題；JPA 把 Java 物件與資料表連接起來；Specification 則避免為每一種搜尋組合都手寫一支 API。

**具體應用情境／舉例**

1. CRM 客戶搜尋頁讓業務組合「產業＝製造業、客戶等級＝A、最近 30 天有互動、負責人＝自己」等條件。Specification 依有值的條件組合查詢，不必建立十幾個固定方法。
2. 新增 `interactions` 表或 `opportunities.stage` 欄位時，新增一個 Flyway migration；另一位同事重建環境後會依相同版本順序得到同樣 schema。
3. 業務新增互動紀錄後關閉 Docker 與 Spring Boot，再重新啟動，資料仍存在；這是持久化真的成立的可見證據。
4. 客戶詳情需要同時讀取商機與互動紀錄時，學生檢查是否產生 N+1 查詢，理解「畫面能顯示」不代表查詢設計已經適合大量資料。

**一句話定位**

> u3 解決的是「資料要留得住、改得有紀錄、查得符合真實業務條件」。

**理解檢核與評估**

這一章的技術密度高，最需要用前後對照降低理解門檻：先示範記憶體 List 重啟即消失，再用 PostgreSQL 保存；先用固定 Query Method，再用 Specification 解決多條件搜尋。評估時應要求提供重啟前後資料與 migration 執行結果。

### u4 Spring Security、JWT、OpenAPI 與企業級錯誤處理

**傳授知識**

- OpenAPI／Swagger：讓 API 契約可閱讀、可測試、可提供給前端。
- `ProblemDetail`、`@RestControllerAdvice`、自訂業務例外與統一錯誤格式。
- Log 層級、`@Slf4j`、Actuator 動態調整 Log 層級與 AOP 的基本概念。
- Authentication 與 Authorization 的差別。
- JWT 三段式結構、Filter、角色資訊與 RBAC。
- 業務、主管、管理員等角色的 API 權限邊界。

**技術用途**

安全技術回答「誰可以進來、可以做什麼」；OpenAPI 回答「前端與測試如何知道 API 怎麼用」；全域錯誤處理與 Log 回答「出錯時使用者看什麼、工程師怎麼追查」。三者一起構成可交付的後端，而不是只會回傳 200 的 Demo。

**具體應用情境／舉例**

1. 業務可以查詢客戶，但只有管理員能刪除客戶：一般使用者收到 403，未登入收到 401，管理員刪除成功收到 204。
2. 前端呼叫不存在的客戶時，所有 Controller 都回傳同一種錯誤結構；前端可以統一顯示錯誤訊息，不必為每一支 API 寫不同解析邏輯。
3. 前端工程師打開 Swagger，輸入 Bearer JWT 後直接測試登入、查客戶與權限差異，減少口頭交接造成的 API 誤用。
4. 生產環境某個套件出現大量警告時，維運人員透過 Actuator 暫時提高 Log 層級，不必為了調查問題重新部署應用程式。

**一句話定位**

> u4 解決的是「資料不應該誰都能看或改，而且出錯時前後端都要知道發生了什麼」。

**理解檢核與評估**

本章內容廣，建議用一條「登入 → 取得 JWT → 帶 Token 查詢 → 不同角色刪除 → 觀察 401／403／404」的流程串起來。AOP、Log 與 OpenAPI 可作為同一個企業後端中「橫切能力」的補充例子，避免學生把它們當成彼此無關的名詞。

### u5 React CRM 工作台與前後端整合

**傳授知識**

- Node.js／NPM 依賴管理與 Vite 初始化 React 19 專案。
- JSX、Functional Component、React State 與前端元件拆分。
- Vite Proxy 解決開發期間前後端來源不同造成的 CORS 問題。
- Axios Interceptor 自動附加 JWT、401 導回登入。
- Loading、Error、Empty、骨架屏與服務健康狀態。
- CRM Dashboard、漏斗、營收預測、風險分布、客戶分群與下鑽。

**技術用途**

前端把 API 能力變成使用者工作流。這一章的重點不是「畫得漂亮」，而是讓業務能快速看到今天該處理什麼、從總覽進入客戶明細，並在登入過期或 API 失敗時得到可理解的狀態。

**具體應用情境／舉例**

1. 業務登入後看到「高風險客戶 3 家」與「本週預計成交金額」，點擊圖表中的高風險區塊後下鑽到 GlobalMart 的互動紀錄。
2. 客戶列表正在等待 API 時顯示骨架屏；沒有符合條件的客戶時顯示 Empty state；服務失敗時顯示重試按鈕，而不是整頁空白。
3. JWT 過期後 API 回傳 401，Axios Interceptor 清除登入狀態並導回登入頁，避免使用者繼續操作一個已失效的畫面。
4. Vite Proxy 讓前端以 `/api/customers` 呼叫後端，開發者不必在每個請求中混入不同環境的 host，也能集中處理 CORS。

**一句話定位**

> u5 解決的是「後端資料如何變成業務每天真的會使用的工作台」。

**理解檢核與評估**

建議把一張 Dashboard 圖表連到真實下鑽結果，讓學生看到視覺元件不是裝飾；再刻意模擬 loading、空資料、401 與後端失敗，驗證狀態處理是否完整。uiuxpromax 的視覺原則可以保留，但應放在資料與互動情境之後。

### u6 Spring AI ChatClient、SSE 與 tool calling

**傳授知識**

- Spring AI `ChatClient`、System Prompt、對話 Session 與模型端點設定。
- Tool Calling：由 Java 工具取得真實 CRM 數字，再交給模型組織語言。
- `@Tool` 與 `ToolCallback` 的選型。
- SSE 單向串流、React `EventSource`、流式 State 與逐字渲染。
- SSE 與 WebSocket 的差異與選型。
- 對話隔離、Spring Security Principal 與 Token 傳遞。
- 風險等級、情緒與意圖等 AI 洞察的呈現。

**技術用途**

ChatClient 負責模型對話整合；Tool Calling 把模型接到可驗證的業務資料；SSE 讓長回應可以邊產生邊顯示。核心安全邊界是「數字由工具計算，文字由模型撰寫」，而不是讓模型自行猜金額、次數或風險。

**具體應用情境／舉例**

1. 業務問：「請整理 GlobalMart 最近狀況與下一步。」後端工具先查最近互動、未解客訴、商機金額與合約日期，模型只負責把資料整理成摘要與建議。
2. 使用者問：「APIM 目前有幾筆進行中的商機？」Tool 回傳數字；若查無客戶，AI 必須說明沒有資料，而不是補一個看似合理的數字。
3. AI 回答較長時，後端透過 SSE 傳送內容事件，前端逐段更新訊息；使用者不必等完整回答產生後才看到第一個字。
4. 兩位業務同時使用聊天室時，以 `sessionId`／Principal 隔離對話，避免 A 使用者看到 B 使用者的歷史內容。
5. 客戶互動中的「預算凍結」被判為負面訊號，系統顯示高風險提醒；但正式的商機狀態或金額仍不能只靠模型文字直接改寫。

**一句話定位**

> u6 解決的是「AI 如何安全地讀取真實業務資料，並以即時對話方式提供建議」。

**理解檢核與評估**

最重要的驗收不是回答看起來自然，而是把 AI 顯示的數字與資料庫逐項比對，並驗證查無資料、越權、Session 隔離與串流錯誤。這也是本章最值得讓學生親手觀察的技術用途。

### u7 團隊智慧分析、全公司評估與 RAG 知識庫

**傳授知識**

- 團隊績效分析、主管 AI 診斷與全公司客戶健康度。
- RAG 與純對話模型的差異，以及 RAG 與 Fine-Tuning 的選用。
- Embedding、文件切分、Metadata、檢索與上下文合併。
- PostgreSQL／pgvector 與 Spring AI VectorStore 的分工。
- 對話歷史非同步向量化、長期記憶、Metadata 隔離與雙路檢索。
- MCP Server／Client、Skills 與外部工具連接（選修）。

**技術用途**

RAG 解決模型不知道公司內部文件、服務條款或最新產品資訊的問題；對話歷史 RAG 解決每次聊天都忘記前情的問題；團隊分析則把多筆 CRM 資料聚合成主管可以採取行動的洞察。MCP 的用途是用一致介面連接外部系統，不是取代 RAG 或 CRM domain tool。

**具體應用情境／舉例**

1. 業務問：「金融客戶可以使用哪種合規方案？」系統先從產品型錄與服務條款找出相關段落，再回答並附上來源；沒有相關文件時明確表示查無資料。
2. 主管查看團隊頁面，看到某位業務負責的客戶中有多家即將續約但近期沒有互動，系統產生優先跟進清單與診斷，而不是只列出原始資料。
3. 使用者上週已與客戶討論預算，本週再次詢問時，系統從具備使用者與客戶 Metadata 的歷史對話找回相關內容，不能把不同使用者或不同客戶的記憶混在一起。
4. 文件上傳後先切片、產生 embedding、寫入 pgvector；SSE 完成後再非同步保存對話，避免向量化延遲拖慢使用者當下的回答。
5. 查 CRM 客戶金額應使用 domain tool；查產品條款應使用 RAG；要建立行事曆事件或寄出 Email，才評估 MCP／外部工具，並保留人工確認。

**一句話定位**

> u7 解決的是「AI 如何根據公司自己的知識、歷史與跨系統能力回答，而不是只靠模型記憶」。

**理解檢核與評估**

建議學生用同一個問題做三次對照：沒有文件時的回答、加入文件後附來源的回答、加入歷史對話後的個人化回答。再要求學生說明 domain tool、RAG、MCP 各自負責什麼，這比背名詞更能確認理解。

### u8 結訓專案衝刺與 Demo Day 驗收

**傳授知識**

- 前後端、JWT、CRM、AI、風險／情緒洞察與 RAG 的端到端整合。
- 三種典型客戶情境的測試案例：高價值、流失風險、續約延遲。
- AI 功能測試：Prompt 組裝、工具呼叫邊界、RAG 檢索，不把模型每次的文字當成唯一測試結果。
- 上線檢查清單：安全、效能、錯誤處理與監控。
- Demo Day 展示順序與可重複驗收流程。

**技術用途**

這一章把「每章各自能跑」轉成「使用者能完成一條工作流程」。它教學生發現整合問題通常不是單一函式錯誤，而是版本、CORS、Token、資料、設定與外部服務之間的邊界沒有對齊。

**具體應用情境／舉例**

1. 展示流程：登入 → 搜尋 GlobalMart → 查看未解客訴 → 請 AI 產生風險摘要 → 查服務條款 → 產生下一步建議。
2. 測試資料庫中的客戶金額與 AI Tool 回傳金額必須相同；若 RAG 沒有命中，不應因 Demo 需要漂亮結果而硬編答案。
3. 學生用一個新環境重新啟動系統，依照清單檢查 DB、JWT、前端 API、SSE 與 RAG，證明流程不是只在自己的瀏覽器狀態中偶然成功。

**一句話定位**

> u8 解決的是「如何證明前面學到的技術真的組成一個可展示、可重跑的產品」。

**理解檢核與評估**

Demo 不應只看畫面是否順利；至少要留下三種客戶情境、角色權限、真實數字、無文件時的行為與測試命令。這一章是把技術用途轉成產品驗收證據的關鍵。

### u9 Cloudflare Tunnel 上線實戰

**傳授知識**

- Docker Compose 編排前端、後端、PostgreSQL／pgvector、cloudflared。
- Cloudflare Tunnel 的 outbound reverse tunnel 與不開入站 port 的網路模型。
- Quick Tunnel 與 Named Tunnel、自有網域、固定網址、Access。
- Volume 持久化、環境變數、CORS、JWT secret 與管理介面保護。

**技術用途**

本章把只有本機能看到的系統變成外部裝置可存取的服務，並示範如何在沒有公網 IP、沒有傳統 port forwarding 的情況下完成展示。它教的是「可安全展示的部署入口」，不是單純取得一個網址。

**具體應用情境／舉例**

1. 學生在家中的電腦啟動 AI CRM，講師用手機 4G 開啟 Quick Tunnel 網址，完成登入、查客戶與 AI 對話；不使用同一個 Wi-Fi 才能證明真的從外部連入。
2. Demo 期間只公開 frontend，nginx 將 `/api` 反代到 backend；資料庫與後端不直接暴露，縮小攻擊面。
3. 臨時課堂展示使用 Quick Tunnel；需要固定網址與長期試用時，再評估 Named Tunnel、自有網域與 Cloudflare Access。
4. `docker compose down` 後再 `up`，客戶資料與向量索引仍然存在，學生可藉此理解 volume 與容器生命週期的差異。

**一句話定位**

> u9 解決的是「怎麼讓別人真的連進你的系統，同時不要把內網直接暴露出去」。

**理解檢核與評估**

應清楚區分 Quick Tunnel 的教學／Demo 性質與正式服務的網域、Access、監控和備份需求。手機 4G 的實際驗收很具體，適合作為本章主要證據。

### u10 Docker 映像打包——從能跑到能交付

**傳授知識**

- 映像作為不可變交付物，以及與「交付原始碼／JAR」的差異。
- 後端與前端多階段 Dockerfile、JDK 建置與 JRE 執行階段。
- `.dockerignore`、建置 context、層快取與 `COPY pom.xml`／`COPY src` 順序。
- 映像體積、`docker history`、版本 tag 與 `latest` 的風險。
- 用 compose 引用已建好的映像做第一次整合測試。

**技術用途**

Docker 映像把程式、依賴與執行環境封裝成可搬運的版本化物件，降低「在我電腦可以跑、換一台就失敗」的風險。多階段建置則把建置工具與原始碼排除在最終執行映像外。

**具體應用情境／舉例**

1. 開發機使用 JDK 21、伺服器沒有 Maven；多階段建置在 build stage 完成 Maven package，執行 stage 只需要精簡 JRE。
2. 只改一行 Java 程式碼時，Docker 仍沿用前面下載好的 Maven 依賴快取，學生從 build log 看出快取是否命中。
3. `ai-crm-backend:1.0.0` 與 `1.1.0` 同時保留，1.1.0 出現問題時仍能回到 1.0.0；使用 `latest` 則容易失去可追溯版本。
4. `.dockerignore` 排除 `.env`、`target`、`node_modules` 與 `.git`，避免秘密進入映像，也縮小建置內容。

**一句話定位**

> u10 解決的是「如何把可運作的程式，變成別人可以拿走且版本清楚的交付物」。

**理解檢核與評估**

不要只驗證 `docker build` 成功；還要檢查映像大小、tag、history、秘密未被打包，以及 compose 使用映像後仍能完成登入與 AI 對話。

### u11 部署到 Docker 伺服器——搬運、上線、更新與退版

**傳授知識**

- 部署三要素：映像、設定、資料分離。
- `docker save`／`docker load` 的離線搬運與 GHCR registry 推拉。
- 伺服器端 compose、`.env`、restart policy、最小對外暴露。
- 版本更新、舊 tag 保留與快速退版。
- Flyway migration 與退版之間的相容性限制。

**技術用途**

本章教的是上線後的日常操作。映像可以換版，設定由環境注入，資料放在 volume；三者分離後，更新與退版才不會把密碼或客戶資料綁死在某一個映像裡。

**具體應用情境／舉例**

1. 內網伺服器不能連 registry 時，用 `docker save` 將版本化映像搬過去，再用 `docker load` 還原；適合教室、隔離網路與緊急救援。
2. 正式伺服器從 `APP_VERSION=1.0.0` 更新到 `1.1.0`，只需 pull 並重新啟動；若前端出現問題，改回舊 tag 退版，volume 中的資料不應消失。
3. `.env` 只存在伺服器，不進 Git；只有 frontend 對外開 port，backend 與 PostgreSQL 留在內部網路。
4. 學生用另一台裝置連伺服器，而不是用伺服器本機的 localhost，驗證服務真的對外提供。

**一句話定位**

> u11 解決的是「如何把版本化系統交給另一台機器運作，並且敢於更新與退回」。

**理解檢核與評估**

核心演練應包含一次更新與一次退版，並記錄版本、容器狀態、資料仍存在的證據。要明確提醒學生：若新版 migration 不可逆，退版不只是換映像 tag，資料庫相容性仍需另行設計。

### u12 Kubernetes 初體驗——用 Docker Desktop 內建叢集部署 AI CRM

**傳授知識**

- Compose 與 Kubernetes 的心智模型差異。
- 宣告式期望狀態、Deployment、Service、ConfigMap、Secret、PVC。
- 本機映像、`imagePullPolicy`、副本數與 port-forward。
- Pod 自癒、滾動更新、rollout undo 與常見排錯狀態。
- 單節點學習環境與生產叢集的差異。

**技術用途**

Compose 適合在一台機器啟動一套服務；Kubernetes 進一步管理副本、健康狀態、更新與多機資源。它的核心不是多背幾個 YAML 欄位，而是把「我要維持什麼狀態」交給叢集持續收斂。

**具體應用情境／舉例**

1. 後端宣告需要 2 個副本，學生手動刪掉一個 Pod，Kubernetes 自動補回；這比只講「自癒」更能讓學生看到技術用途。
2. 更新 backend 映像時，Kubernetes 先啟動新副本，健康後再替換舊副本；服務不中斷，出問題時用 `rollout undo` 退版。
3. 非敏感環境設定放 ConfigMap，JWT secret 與資料庫密碼放 Secret；學生同時理解 Secret 的 base64 不是加密，不能因此把秘密提交到 Git。
4. Deployment 管無狀態前後端，PostgreSQL 使用 PVC 保留資料；並說明正式環境通常會優先使用託管資料庫，而不是把單節點學習設定直接搬上生產。

**一句話定位**

> u12 解決的是「當服務需要自動補副本、平滑換版與集中管理時，如何從手動容器管理走向宣告式平台」。

**理解檢核與評估**

至少要實際完成 `kubectl get nodes`、登入與 AI 對話、刪 Pod 看自動重生、滾動更新與退版。文件應清楚標示 Docker Desktop Kubernetes 是學習環境，不應讓學生把單節點 port-forward 誤認成完整生產架構。

## 五、建議的學生理解節奏

若要讓學生快速抓到用途，每章開頭可以先用同一種敘事順序說明：

1. **先看業務問題**：例如業務找不到高風險客戶、資料重啟消失、AI 算錯金額、換版造成服務中斷。
2. **再指出技術責任**：資料庫、JWT、React、Tool Calling、RAG、Docker 或 Kubernetes 各自只解決其中一段。
3. **再看最小操作**：一個 API、一張畫面、一個 Docker 指令或一次 `kubectl` 實驗。
4. **最後看失敗案例**：錯誤輸入、無權限、無資料、無文件、容器重啟、版本退回。

最值得固定成全課共同語言的句型是：

> 業務想完成「某個操作」；系統需要「某項能力」；所以使用「某項技術」；最後用「某個可觀察結果」驗收。

例如：

> 業務想知道 GlobalMart 是否有流失風險；系統需要讀取最近互動與商機資料；所以用 Tool Calling 取得真實數字，再由 ChatClient 組織摘要；最後比對資料庫數字與前端風險卡片。

## 六、最終判定

目前 `teaching-site` 的技術內容具備實際應用情境，且 AI CRM 主題可以把 12 個單元串成完整產品路線。真正需要評估的不是「有沒有用途」，而是每章是否在學生看到技術名詞的當下，立刻讓他知道：

- 這項技術替誰解決什麼問題。
- 不使用它時會發生什麼具體麻煩。
- 在 AI CRM 的哪個畫面、API 或部署流程會用到它。
- 學生要觀察哪個結果，才算真的理解而不是只完成指令。

因此，若後續要補強網站內容，優先順序建議是：

1. 先補 u1、u3、u4、u9、u12 的「技術價值橋接句」，讓基礎設施與部署章節不會像獨立工具教學。
2. 保留 u2、u5、u6、u7 的 CRM 操作情境，並持續要求使用真實資料、來源與權限驗證。
3. 將 u8–u12 的驗收結果寫成可見證據：HTTP／UI 結果、重啟後資料、外部裝置連線、映像版本、Pod 狀態與退版結果。
4. 任何涉及正式生產的說明，都要分開標示「課程學習環境」與「實際生產還需要的治理與維運」。

# 寄信之前，先把 DNS 設對

### 一本給開發者的 Email 認證與送達率指南

---

## 前言：這本書要解決的問題

你把功能做完了。註冊信、通知信、電子報，程式都跑得好好的，API 回 200，log 顯示 `sent`。

然後你收到一則訊息：

> 「我沒收到信耶。」

你去垃圾郵件匣一看，信在那裡。或者更糟——信根本不見了，收件伺服器連退信都沒給你。

這時候你會發現一件事：**寄信這件事，程式碼只佔一半。另一半在 DNS 裡。**

收件伺服器不認識你的程式，它只認得你的網域，以及你在 DNS 上留下的那幾行字。那幾行字決定了它要不要相信「這封聲稱來自 `你的網域` 的信，真的是你寄的」。

這本書要講的就是那幾行字：它們各自在回答什麼問題、語法怎麼寫、為什麼順序和數量會出錯，以及出錯的時候怎麼查。

**適合誰讀**：自己架過或正要架寄信功能的開發者。你不需要懂 DNS 底層，但你需要能看懂 `v=spf1 include:...` 這種東西在說什麼。

**不需要什麼**：不需要自己架 mail server。事實上這本書的預設情境就是你用第三方寄信服務（SendGrid、Resend、Amazon SES、Mailgun、Postmark、Zeabur ZSend⋯⋯），因為那是絕大多數人的實際狀況。

---

## 第 1 章：收件伺服器在問三個問題

一封信送到 Gmail 門口，Gmail 不會直接讓它進去。它會問三個問題：

**問題一：這封信真的是從那個網域授權的伺服器寄出的嗎？**
→ 這是 **SPF** 在回答的。

**問題二：這封信在路上有沒有被改過？寄件網域願意為它背書嗎？**
→ 這是 **DKIM** 在回答的。

**問題三：如果前兩題沒過，我該怎麼處理這封信？而且，你希望我把結果回報給誰？**
→ 這是 **DMARC** 在回答的。

這三個是 email 認證的核心，缺一不可。它們不是三選一，也不是「設一個就夠了」——2024 年起 Gmail 和 Yahoo 對大量寄件者（每天 5000 封以上）的要求就是三個全部都要有。

還有一個常常被誤會的角色：

**MX** 回答的是完全不同的問題——**「別人要寄信給這個網域，該送到哪台伺服器？」**

MX 管的是**收信**，跟你能不能寄信出去**一點關係都沒有**。這是新手最常見的誤解之一，第 2 章會專門講。

## 第 2 章：先分清楚「收信」和「寄信」

這一章很短，但它會幫你省下好幾個小時的困惑。

### 寄信和收信是兩條完全獨立的路

| | 收信 | 寄信 |
|---|---|---|
| 靠哪個紀錄 | MX | SPF / DKIM / DMARC |
| 沒設會怎樣 | 別人寄給你的信直接退回 | 你寄出去的信被當垃圾信 |
| 誰在讀這個紀錄 | 想寄信給你的伺服器 | 收到你的信的伺服器 |

**你可以只寄不收**：很多產品的寄件位址是 `noreply@example.com`，網域上根本沒有 MX 紀錄。信寄得出去，但沒人能回信（回信會直接彈回）。

**你也可以只收不寄**：把網域的 MX 指向轉寄服務，讓 `contact@example.com` 轉到你平常用的信箱。這種情況下你**不需要**動 SPF——轉寄服務只是幫你收信，沒有用你的網域寄信。

搞清楚這件事，你才不會在「我只是想加個聯絡信箱」的時候，去亂動 SPF 而把原本正常的寄信搞壞。（第 8 章會看到一個真實案例，就是這樣壞掉的。）

### 一個常見的誤會

> 「我的 MX 設好了，為什麼寄出去的信還是進垃圾桶？」

因為 MX 跟你寄信完全無關。收件方在判斷「要不要相信這封信」的時候，根本不會去查你的 MX。

## 第 3 章：SPF — 誰可以用我的網域寄信

**SPF**（Sender Policy Framework，寄件者政策框架）是一份**白名單**。你在 DNS 上公告：「只有這些伺服器，可以用我的網域寄信。」

收件伺服器收到信之後，看一下這封信是從哪個 IP 來的，再去查你的 SPF，比對「這個 IP 在名單上嗎」。

### 長什麼樣子

SPF 是一筆 **TXT 紀錄**，放在網域根目錄：

```
類型：TXT
名稱：@            （代表網域本身，有些後台要填完整網域名）
內容：v=spf1 include:_spf.google.com include:sendgrid.net ~all
```

拆開來看：

| 片段 | 意思 |
|---|---|
| `v=spf1` | 版本宣告。**必須是開頭**，沒有這個就不算 SPF 紀錄 |
| `include:_spf.google.com` | 「Google 那份名單上的伺服器，也算我授權的」 |
| `include:sendgrid.net` | 同上，SendGrid 的也算 |
| `~all` | 「以上都不符合的話，算**軟性失敗**」 |

### 結尾那個符號很重要

最後的 `all` 前面那個符號，決定了「不在名單上的寄件者」要怎麼處理：

| 寫法 | 名稱 | 意思 | 建議 |
|---|---|---|---|
| `-all` | Fail（硬失敗） | 「不在名單上的，一律當偽造」 | 確定名單完整後再用 |
| `~all` | SoftFail（軟失敗） | 「不在名單上的很可疑，但先別直接丟掉」 | **新手從這個開始** |
| `?all` | Neutral | 「我不表態」 | 幾乎等於沒設，不建議 |
| `+all` | Pass | 「誰都可以用我的網域寄信」 | **絕對不要用**，等於開放偽造 |

實務建議：**剛設定時用 `~all`，觀察一到兩週的 DMARC 報告，確認沒有漏掉合法的寄件來源之後，再改成 `-all`。**

直接上 `-all` 的風險是：你可能忘記某個系統也在用這個網域寄信（客服系統、電子報平台、CRM、發票系統、監控告警⋯⋯），一改就全掛。

### 三個會讓你踩坑的規則

#### 規則一：一個網域只能有**一筆** SPF

這是最常見、也最致命的錯誤。

網域上可以有很多筆 TXT 紀錄（Google 驗證碼、各種服務的驗證字串都是 TXT），這沒問題。**但其中只能有一筆是以 `v=spf1` 開頭的。**

如果有兩筆，收件伺服器會回報 `PermError`（永久錯誤），結果是 **SPF 直接失效**——不是「兩筆都生效」，也不是「取其中一筆」，而是**兩筆都不算數**。

```
❌ 錯誤示範
TXT  @  v=spf1 include:_spf.google.com ~all
TXT  @  v=spf1 include:sendgrid.net ~all
```

```
✅ 正確做法：合併成一筆
TXT  @  v=spf1 include:_spf.google.com include:sendgrid.net ~all
```

**所以每次新增寄信服務，你要做的是「編輯既有那一筆」，不是「新增一筆」。** 很多服務商的說明文件會叫你「新增一筆 TXT」，如果你網域上已經有 SPF，照做就爆了。

#### 規則二：最多 10 次 DNS 查詢

SPF 在解析時，每個 `include:`、`a`、`mx`、`exists`、`redirect=` 都會觸發一次 DNS 查詢。而且 `include` 是遞迴的——你 include 別人，別人的紀錄裡如果又有 include，也一起算。

**總數超過 10 次，SPF 直接 `PermError` 失效。**

`ip4:`、`ip6:`、`all` 不算查詢次數，所以真的擠不下的時候，可以把某些 include 展開成 IP 區段（但缺點是對方換 IP 你不會知道）。

怎麼檢查？用線上工具（後面第 9 章會列）看它算出來的 lookup 次數。四五個 include 就該開始注意了。

#### 規則三：SPF 檢查的不是你以為的那個寄件人

這是理解 DMARC 的關鍵，也是最反直覺的一點。

一封信有**兩個**寄件位址：

- **信封寄件人**（envelope sender / `MAIL FROM` / `Return-Path`）：SMTP 協定層的，收件人**看不到**。退信會寄到這裡。
- **信頭寄件人**（`From:` 標頭）：收件人在信箱裡**看到的那個**。

**SPF 檢查的是信封寄件人，不是 `From:`。**

這造成一個常見現象：你用第三方服務寄信，服務商把信封寄件人設成他們自己的網域（例如 `bounces.sendgrid.net`），SPF 查的是 SendGrid 的紀錄——**通過了**，但這跟你的網域一點關係都沒有。

收件人看到的是 `you@example.com`，SPF 驗的卻是 `sendgrid.net`。這兩個對不起來，就是第 6 章要講的「對齊」問題。

## 第 4 章：DKIM — 信件的防偽封條

**DKIM**（DomainKeys Identified Mail）用的是**非對稱加密**。

寄信時，寄件伺服器用**私鑰**對信件的內容和部分標頭做簽章，把簽章塞進 `DKIM-Signature` 標頭。收件方從你的 DNS 取得**公鑰**，驗證這個簽章。

驗過了，代表兩件事：

1. 這封信確實是握有私鑰的人寄的（身分）
2. 信件在傳送過程中沒有被竄改（完整性）

### 長什麼樣子

DKIM 的 TXT 紀錄放在一個特別的位置：

```
類型：TXT
名稱：selector._domainkey          （例如 zeabur._domainkey）
內容：v=DKIM1; k=rsa; p=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8AMIIBCgKCAQEA...
```

| 片段 | 意思 |
|---|---|
| `v=DKIM1` | 版本 |
| `k=rsa` | 金鑰演算法 |
| `p=...` | **公鑰本體**（Base64，通常很長） |

### 什麼是 selector（選擇器）

`selector` 是你自己取的名字，它讓**同一個網域可以同時有多把金鑰**。

這件事很重要，因為：

- 你可能同時用兩家寄信服務，各自需要一把金鑰 → 用不同 selector 就不會打架
- 金鑰需要定期輪替 → 先放新 selector，切換過去，再刪掉舊的，全程零中斷

簽章裡會寫明用的是哪個 selector（`s=` 欄位），收件方就知道要去 `那個selector._domainkey.你的網域` 找公鑰。

### DKIM 的關鍵優勢：撐得過轉寄

這是 DKIM 跟 SPF 最大的差別。

**SPF 一轉寄就壞掉。** 因為轉寄之後，寄件 IP 變成轉寄伺服器的 IP，而它一定不在你的 SPF 名單上。這是 SPF 的先天限制，不是設定錯誤。

**DKIM 不受影響**（只要信件內容沒被改動）。簽章跟著信件走，轉寄幾次都還在。

這也是為什麼 DMARC 允許「SPF **或** DKIM 其中一個通過就好」——因為 SPF 在轉寄情境下必然失敗，如果要求兩個都過，所有郵件論壇和轉寄服務都會爛掉。

### 實務上會遇到的坑

**2048 位元金鑰太長，塞不進單一 TXT 字串。** DNS 的單一字串上限是 255 字元，2048 位元的公鑰會超過。正確做法是在**同一筆紀錄內**切成多段引號字串：

```
"v=DKIM1; k=rsa; p=MIIBIjANBgkq..." "...剩下的部分"
```

多數 DNS 後台會自動處理，但有些需要你手動貼成這個格式。如果 DKIM 一直驗不過，先檢查這裡。

**私鑰不會出現在 DNS 上。** DNS 上只有公鑰。私鑰在寄信服務商那邊（如果是他們代管），或在你的伺服器上。看到有人叫你把私鑰貼進 DNS，那是錯的。

## 第 5 章：DMARC — 沒通過的時候怎麼辦

SPF 和 DKIM 各自回答了「這封信可不可信」，但它們沒有回答**「不可信的時候該怎麼辦」**。

以前這是收件伺服器自己猜的。**DMARC**（Domain-based Message Authentication, Reporting and Conformance）讓網域擁有者可以明確宣告處置方式，而且——這點常被低估——**可以要求收件方定期回報統計資料給你**。

### 長什麼樣子

```
類型：TXT
名稱：_dmarc
內容：v=DMARC1; p=none; rua=mailto:dmarc@example.com; adkim=r; aspf=r
```

| 標籤 | 意思 | 常用值 |
|---|---|---|
| `v=DMARC1` | 版本，**必須第一個** | 固定 |
| `p=` | 驗證失敗時的處置政策 | `none` / `quarantine` / `reject` |
| `sp=` | **子網域**的政策 | 省略時繼承 `p` |
| `rua=` | 彙總報告寄到哪 | `mailto:` 位址 |
| `ruf=` | 鑑識報告（單封失敗明細） | 多數服務商已不寄，隱私考量 |
| `adkim=` | DKIM 對齊嚴格度 | `r`（寬鬆，預設）/ `s`（嚴格） |
| `aspf=` | SPF 對齊嚴格度 | `r` / `s` |
| `pct=` | 套用政策的比例 | `1`–`100` |

### 三種政策，照順序走

**`p=none`——只觀察，不處置。**

這是**起點，不是終點**。它不會影響任何郵件的投遞，唯一的作用是讓你開始收到 `rua` 報告。

先用它跑一到兩週，從報告裡確認：有哪些來源在用你的網域寄信？其中哪些是你認得的？哪些沒通過驗證？

很多人會在報告裡發現自己完全忘記的系統——舊的電子報平台、公司的發票系統、某個同事設定的自動通知。這正是 `p=none` 的價值。

**`p=quarantine`——可疑的丟進垃圾桶。**

確認合法來源都通過驗證之後，往前走一步。

**`p=reject`——直接拒收。**

最終目標。到這一步，冒用你網域的釣魚信會在門口就被擋下，根本不會進到收件人的信箱。

**不要跳級。** 直接上 `p=reject` 而漏掉某個合法寄件來源，那個來源的信會**全部消失**，而且你可能好幾天後才會知道。

### 致命細節：`_dmarc` 只能有一筆紀錄

跟 SPF 一樣，而且後果一樣嚴重。

RFC 7489 §6.6.3 寫得很明白：如果在 `_dmarc.你的網域` 找到**多筆** DMARC 紀錄，收件方的處理方式是——**當作你完全沒有設 DMARC**。

不是取第一筆，不是取最嚴格的那筆，是**整個當作不存在**。

這個錯誤特別陰險，因為：

- 網域註冊商有時會**自動幫你加**一筆預設的 DMARC
- 你自己設的那筆看起來完全正確
- 用一般的 DNS 查詢工具，如果只看第一筆回應，你會以為設好了
- 信還是照常寄得出去（因為 DMARC 失效等於沒有限制），所以**沒有任何徵兆**

第 8 章會看到一個真實案例。

## 第 6 章：Alignment 對齊 — 最多人卡住的地方

如果這本書你只記得一章，記這章。

**「SPF 通過了，DKIM 也通過了，為什麼 DMARC 還是失敗？」**——這是 email 認證裡最常見的困惑，答案幾乎都是對齊。

### DMARC 要的不只是「通過」

DMARC 的判定條件是：

> （SPF 通過 **且** SPF 對齊）**或**（DKIM 通過 **且** DKIM 對齊）

「通過」和「對齊」是**兩件事**，要同時滿足。

**什麼是對齊**：驗證的那個網域，必須跟收件人**看到的** `From:` 網域是同一個。

| | 驗證的是哪個網域 | 要跟什麼對齊 |
|---|---|---|
| SPF 對齊 | 信封寄件人（`Return-Path`）的網域 | `From:` 標頭的網域 |
| DKIM 對齊 | 簽章裡 `d=` 的網域 | `From:` 標頭的網域 |

### 為什麼會不對齊

典型情境：你用第三方服務寄信。

```
From:         news@example.com          ← 收件人看到的
Return-Path:  bounce@mail.esp-vendor.com ← SPF 驗這個
DKIM d=       esp-vendor.com             ← DKIM 驗這個
```

SPF 查 `esp-vendor.com` 的紀錄 → **通過**。
DKIM 用 `esp-vendor.com` 的公鑰 → **通過**。
DMARC 看：驗過的都是 `esp-vendor.com`，但 `From:` 是 `example.com` → **兩邊都不對齊 → DMARC 失敗**。

信件認證全綠，DMARC 卻是紅的。

### 怎麼修

**修 DKIM 對齊**（比較常見，也比較簡單）：在寄信服務商後台完成「網域驗證」流程，讓它用**你的網域**簽章（`d=example.com`），而不是它自己的。這通常就是它叫你去 DNS 加 DKIM 紀錄的原因。

**修 SPF 對齊**：設定「自訂回信網域」（custom return-path / custom bounce domain），通常是加一筆 CNAME 讓 `bounce.example.com` 指向服務商，這樣信封寄件人就變成你的子網域了。

**兩個修好一個就夠**（DMARC 是 OR 條件）。但兩個都修最穩——因為轉寄會打壞 SPF，只剩 DKIM 撐著。

### 寬鬆 vs 嚴格

`adkim` / `aspf` 控制對齊的比對方式：

| 模式 | 寫法 | `From: news@example.com` 時 |
|---|---|---|
| 寬鬆（relaxed） | `r`（預設） | `mail.example.com` **算對齊**（同一個組織網域） |
| 嚴格（strict） | `s` | 必須**完全等於** `example.com` |

**除非你很清楚自己在做什麼，用預設的寬鬆就好。** 嚴格模式會讓子網域寄信失敗，而你的服務商很可能就是用子網域。

## 第 7 章：其他你可能會遇到的紀錄

前面五個（MX / SPF / DKIM / DMARC + 對齊）是必修。這章是選修，但知道它們存在會有幫助。

### PTR / 反向 DNS

從 IP 反查主機名稱。收件方會檢查：這個 IP 反查得到主機名嗎？那個主機名再正查回來，是同一個 IP 嗎？

**用第三方寄信服務的話，這是服務商的責任，你不用管。** 只有自架 mail server 才需要處理（要跟你的 IP 供應商申請設定）。

自架而沒設 PTR，信幾乎必進垃圾桶。

### BIMI — 讓你的 Logo 出現在信箱裡

```
名稱：default._bimi
內容：v=BIMI1; l=https://example.com/logo.svg; a=https://example.com/vmc.pem
```

前提條件很硬：

- DMARC 必須是 `p=quarantine` 或 `p=reject`（`p=none` 不行）
- Logo 必須是 SVG Tiny PS 格式
- Gmail 等主流服務還要求 **VMC**（已驗證標章憑證），那是要付費申請的，一年數萬元起跳

**這是錦上添花，不是必需品。** 把前面五個做好再考慮。

### MTA-STS 與 TLS-RPT — 傳輸加密

MTA-STS 要求寄給你的伺服器必須用 TLS 加密連線，防止降級攻擊。它需要 DNS 紀錄**加上**一個 HTTPS 端點：

```
名稱：_mta-sts
內容：v=STSv1; id=20260801000000
```

政策檔要放在 `https://mta-sts.example.com/.well-known/mta-sts.txt`。

TLS-RPT 則是收 TLS 相關的失敗報告：

```
名稱：_smtp._tls
內容：v=TLSRPTv1; rua=mailto:tlsrpt@example.com
```

**這兩個保護的是「別人寄給你」的路徑**，跟你寄信出去的送達率無關。

### 子網域策略：把電子報跟正事分開

一個實務上很值得的做法：**用子網域寄行銷信**。

```
交易信（密碼重設、訂單通知）：example.com
行銷信（電子報、促銷）：       news.example.com
```

理由是**信譽隔離**。電子報一定會有人按「檢舉垃圾信」，這會傷害寄件網域的信譽。如果兩者共用同一個網域，某天電子報被大量檢舉，你的密碼重設信也會跟著進垃圾桶——那是會讓使用者登不進去的等級的事故。

用子網域隔開，行銷信的信譽問題就燒不到主網域。

搭配 DMARC 的 `sp=` 標籤可以給子網域不同政策。

## 第 8 章：實戰體檢 — 一個真實網域的三個問題

理論講完了。這章用一個**真實的、正在營運的**網域來做體檢：`springai.world`。

這個網域用 Zeabur ZSend 寄電子報（寄件人 `noreply@springai.world`），用 ImprovMX 做 `contact@` 的收信轉寄。

以下紀錄由 8.8.8.8、1.1.1.1、9.9.9.9 三個公開 resolver 交叉查詢確認，結果一致。

### 目前的實際狀態

```
MX      springai.world       10  mx1.improvmx.com
                             20  mx2.improvmx.com

TXT     springai.world       google-site-verification=0IrjUcCG...
                             v=spf1 include:spf.improvmx.com ~all

TXT     _dmarc.springai.world
                             v=DMARC1; p=quarantine; adkim=r; aspf=r; rua=mailto:dmarc_rua@onsecureserver.net;
                             v=DMARC1; p=none;
```

### 問題一：DMARC 有兩筆 → 等於完全沒設

`_dmarc.springai.world` 底下有**兩筆** `v=DMARC1` 紀錄。

依照第 5 章講的 RFC 7489 §6.6.3，收件方的處理是**當作沒有 DMARC**。

所以那筆看起來很認真的 `p=quarantine`——指定了對齊模式、還設了報告收件位址——**完全沒有在運作**。而且因為 DMARC 失效只是「少了一層保護」而不是「信寄不出去」，所以從外部完全看不出徵兆。

那筆 `p=none;` 從 `rua` 位址是 `onsecureserver.net`（GoDaddy 的網域）推測，很可能是註冊商自動加上的預設值。

**這正是第 5 章說的那個陰險錯誤的實例。**

修法：刪掉 `v=DMARC1; p=none;` 那一筆，只留完整的那筆。

### 問題二：SPF 只授權了 ImprovMX，寄信服務不在名單上

```
v=spf1 include:spf.improvmx.com ~all
```

`spf.improvmx.com` 展開後全是 ImprovMX 的 IP（`195.154.155.118`、`51.158.91.128/28` 等等）。

**這裡面沒有任何 ZSend／Zeabur 的來源。**

回頭看第 2 章：ImprovMX 在這個架構裡負責的是**收信轉寄**，而收信轉寄**根本不需要 SPF**（只需要 MX）。所以現在的狀況是——SPF 授權了一個不需要被授權的服務，卻沒有授權真正在寄信的那個。

從施工紀錄看，原本網域上是有 ZSend 的 SPF 的。加 ImprovMX 的時候，服務商的說明文件通常會說「新增一筆 SPF」，而因為第 3 章講的「只能有一筆」規則，正確做法是**合併**——看來這裡是**覆蓋**掉了。

這是第 3 章規則一的實例，而且是它最常見的發生方式。

### 問題三：找不到 DKIM

我探測了 17 個常見的 selector（`zeabur`、`zsend`、`default`、`mail`、`selector1`⋯⋯），**全部沒有回應**。

DKIM 的 selector 是服務商自訂的，猜不到不代表沒有——所以這一項我**不能斷定**。但配合前兩項一起看，值得你親自確認。

### 這三個加起來的意思

現在的狀況大概是這樣：

- SPF 對 ZSend 寄出的信**不通過**（IP 不在名單上）
- DKIM 狀態**未知**
- DMARC **失效**，所以前兩項的失敗**不會被處置**

換句話說——**信目前還寄得出去，正是因為 DMARC 壞掉了**。

這是最危險的那種狀態：表面上一切正常，但保護是空的。而且一旦哪天 DMARC 被修好（例如註冊商調整了預設值，或你自己去刪掉一筆），`p=quarantine` 立刻生效，而 SPF 又不通過——**電子報會在同一天集體進垃圾桶**，你還會以為是修 DMARC 修壞的。

### 建議的修復順序

**順序很重要。先讓驗證通過，再啟用處置。**

1. **先修 SPF**：把寄信服務的 include 加回去，跟 ImprovMX 合併成一筆
   ```
   v=spf1 include:<寄信服務的SPF主機> include:spf.improvmx.com ~all
   ```
   （實際要 include 什麼，去寄信服務商的網域驗證頁面查）

2. **確認 DKIM**：到寄信服務商後台完成網域驗證，把它給的 DKIM 紀錄加上去

3. **確認對齊**：寄一封測試信給自己，看原始信件標頭（Gmail 是「顯示原始郵件」），檢查 `Return-Path` 和 DKIM 的 `d=` 是不是你的網域

4. **最後才處理 DMARC**：刪掉多餘那筆，並且**先降成 `p=none`** 觀察一到兩週，確認報告裡合法來源都通過了，再逐步調回 `quarantine`

**千萬不要反過來**——先修好 DMARC 而 SPF/DKIM 還沒過，等於親手把自己的信全部送進垃圾桶。

## 第 9 章：驗證與除錯

### 命令列查詢

**Windows（PowerShell）**：

```powershell
# SPF（在一堆 TXT 裡挑出 SPF 那筆）
(Resolve-DnsName example.com -Type TXT -Server 8.8.8.8).Strings | Where-Object { $_ -like 'v=spf1*' }

# DMARC —— 注意要看「有幾筆」，不是只看第一筆
Resolve-DnsName _dmarc.example.com -Type TXT -Server 8.8.8.8

# DKIM（selector 換成你的）
Resolve-DnsName selector._domainkey.example.com -Type TXT -Server 8.8.8.8

# MX
Resolve-DnsName example.com -Type MX -Server 8.8.8.8
```

**macOS / Linux**：

```bash
dig +short TXT example.com @8.8.8.8
dig +short TXT _dmarc.example.com @8.8.8.8
dig +short TXT selector._domainkey.example.com @8.8.8.8
dig +short MX example.com @8.8.8.8
```

### 三個查詢時的實務提醒

**一、指定 resolver，而且查不只一個。** 直接 `dig TXT example.com` 會用你本機的 DNS，可能有快取。指定 `@8.8.8.8`（Google）、`@1.1.1.1`（Cloudflare）、`@9.9.9.9`（Quad9），三個都查。改完 DNS 之後，這也是確認「傳播完成了沒」最快的方法。

**二、一定要看紀錄「筆數」。** 這是本書最重要的除錯技巧。用 `+short` 或只看第一行，會漏掉「有兩筆 SPF」「有兩筆 DMARC」這類問題——而它們是最常見也最難察覺的錯誤。

**三、TTL 決定你要等多久。** 改了 DNS 沒立刻生效是正常的。舊值的 TTL 是多少，最久就要等多久。要改設定前，可以先把 TTL 調短（例如 300 秒），等生效後再改值，這樣試錯會快很多。

### 最有效的除錯手段：讀信件原始標頭

線上工具再多，都不如直接看一封**真實寄出**的信。

寄一封測試信到你的 Gmail，打開信件 →「顯示原始郵件」，找這幾行：

```
Authentication-Results: mx.google.com;
       dkim=pass header.d=example.com;
       spf=pass (google.com: domain of bounce@example.com designates ... as permitted sender)
       dmarc=pass (p=NONE sp=NONE dis=NONE) header.from=example.com
```

這幾行是**收件方的實際判定結果**，比任何預測工具都準：

- `dkim=pass header.d=` → 後面那個網域是不是**你的**？是的話 DKIM 對齊沒問題
- `spf=pass ... domain of` → 後面那個位址的網域是不是**你的**？
- `dmarc=` → 最終結論
- `header.from=` → 收件人看到的網域

**只要 `dkim=pass` 而且 `header.d=` 是你的網域，DMARC 就會過**，SPF 那邊怎樣都無所謂。

### 線上工具

| 工具 | 用途 |
|---|---|
| `mxtoolbox.com` | 綜合查詢，SPF lookup 次數會幫你算 |
| `dmarcian.com/dmarc-inspector` | DMARC 語法檢查 |
| `mail-tester.com` | 寄一封信給它，給你 10 分制評分與逐項問題 |
| `learndmarc.com` | 視覺化展示整個驗證流程，適合搞懂對齊 |

其中 **mail-tester 最推薦**，因為它做的是端到端實測，不是只讀 DNS。

### DMARC 報告怎麼看

設了 `rua` 之後，收件方會每天寄 XML 給你。生 XML 很難讀，實務上有兩條路：

1. **用託管服務**（Postmark DMARC、dmarcian、URIports 等有免費額度），把 `rua` 指過去，它給你網頁報表
2. 自己寫個 parser（如果你就是想練手）

報告裡最該看的是：**有哪些 IP 用你的網域寄信，但驗證沒過？** 那些要嘛是你忘記的合法系統（要加進 SPF），要嘛是有人在冒用你的網域（那就更該把 DMARC 調嚴）。

## 第 10 章：十個常見陷阱

**一、兩筆 SPF。** 每次新增服務要**編輯**既有那筆，不是新增。後果：SPF 完全失效。

**二、兩筆 DMARC。** 常常是註冊商自動加的。後果：DMARC 完全失效，且無徵兆。

**三、SPF 超過 10 次 lookup。** include 是遞迴計算的。後果：`PermError`，SPF 失效。

**四、以為設了 MX 就能寄信。** MX 只管收信。

**五、直接上 `p=reject`。** 一定要從 `p=none` 開始觀察。

**六、只看第一筆查詢結果。** 會漏掉重複紀錄，也就是陷阱一和二。

**七、忽略對齊。** SPF/DKIM 都 pass 但 DMARC fail，答案幾乎都在這裡。

**八、DKIM 公鑰被截斷。** 2048 位元金鑰超過單一 TXT 字串 255 字元上限，要切段。

**九、忘記某個系統也在用這個網域寄信。** 發票、客服、CRM、監控告警⋯⋯先用 `p=none` 收報告就是在找這些。

**十、以為改完 DNS 立刻生效。** TTL 沒過就是沒過。用三個公開 resolver 交叉確認。

## 附錄 B：名詞速查

| 名詞 | 一句話解釋 |
|---|---|
| **MX** | 別人要寄信給這個網域時，送到哪台伺服器。只管收信。 |
| **SPF** | 白名單，宣告哪些伺服器可以用我的網域寄信。查的是信封寄件人。 |
| **DKIM** | 用私鑰簽章、公鑰驗證，證明信件沒被改過。撐得過轉寄。 |
| **DMARC** | 前兩者失敗時怎麼處置，以及把統計報告寄給誰。 |
| **Alignment（對齊）** | 驗證的網域必須跟收件人看到的 `From:` 網域一致。 |
| **Selector（選擇器）** | DKIM 金鑰的名字，讓同一網域能有多把金鑰、能輪替。 |
| **信封寄件人** | SMTP 層的寄件位址，收件人看不到，退信寄回這裡。SPF 驗這個。 |
| **`From:` 標頭** | 收件人實際看到的寄件人。DMARC 保護的是這個。 |
| **PTR / rDNS** | IP 反查主機名。自架才要管，用 SaaS 是服務商的事。 |
| **BIMI** | 讓 Logo 顯示在收件匣。需要嚴格 DMARC，Gmail 還要付費憑證。 |
| **TTL** | 這筆紀錄可以被快取多久。決定你改完要等多久。 |
| **PermError** | SPF 語法或結構錯誤（重複、超過 lookup 上限），結果等同驗證失敗。 |

## 結語

回到開頭那句「我沒收到信耶」。

現在你知道要問的不是「程式是不是壞了」，而是：

1. 這封信的 `Authentication-Results` 長什麼樣？
2. SPF 和 DMARC 各有幾筆？
3. `dkim=pass` 的 `header.d=` 是我的網域嗎？

三個問題，五分鐘之內能查完，涵蓋絕大多數的送達率問題。

而第 8 章那個真實案例想說的是：**這些設定不會壞得很大聲。** 它們壞掉的時候，信照樣寄得出去，後台照樣顯示成功，沒有任何錯誤訊息。直到某天你發現開信率掉了一半，或者有人跟你說「你們的信都在垃圾桶」。

所以定期體檢比什麼都重要。把附錄 A 的清單存起來，每次動 DNS 之後跑一遍。

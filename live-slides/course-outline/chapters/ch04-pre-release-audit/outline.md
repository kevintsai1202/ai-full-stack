# Ch04：將上線風險轉成基準式稽核

## 章節摘要

把「幫我看看有沒有資安漏洞」改成依外部基準逐項檢查的稽核。第一層檢查 IssueFlow 自有程式碼，第二層檢查第三方相依套件；報告必須列出命中、未命中與不適用理由。最後實際重現一項問題並修補，清楚區分 AI 輔助稽核與正式滲透測試。

**Unit ID**：`d2-u2`

## 來源投影片

- P34–P36：上線前、基準式稽核與 OWASP／CWE 提示詞
- P37–P41：稽核摘要、A10 案例、相依套件、修補對比與限制
- P42：Q4
- P43–P46：Q0 回收、四句型總表、Q5 與 Q&A

## 學習目標

- 能夠使用 OWASP／CWE 清單建立逐項稽核表。
- 能夠列出未命中項目並說明不適用原因，而不是只挑幾個問題。
- 能夠盤點直接與間接相依套件，理解「今天乾淨」的限制。
- 能夠修補一個可重現的資訊洩漏或錯誤處理問題，並保留前後證據。
- 能夠說明 AI 稽核不能取代滲透測試的原因。

## 核心主題

1. Baseline audit：有清單才有覆蓋率。
2. 自有程式碼與第三方相依套件是兩個不同稽核面向。
3. 對外回應與內部日誌的資訊分流。
4. 稽核全綠只代表清單看過，不代表系統絕對安全。

## IssueFlow 專案作業任務

- `d2-u2-t1`：對照 OWASP／CWE 建立 IssueFlow 基準表，列出命中、未命中、位置、證據與不適用原因。
- `d2-u2-t2`：盤點專案直接相依套件與版本，記錄 `npm audit`、lockfile 與實際執行日期。
- `d2-u2-t3`：重現一個 IssueFlow 錯誤回應洩漏檔案系統路徑或內部細節的案例。
- `d2-u2-t4`：修補為制式對外訊息，保留必要內部日誌，重跑測試與稽核並整理最終展示。

## 驗收標準

- 稽核表同時包含命中與未命中項目，未命中項目有原因。
- 至少一個問題有「修補前回應／修補後回應／測試或日誌證據」。
- 能區分自有程式碼稽核、相依套件稽核與滲透測試。
- 結訓回顧能把四章產物串成一條「評估 → 計畫 → 驗證 → 稽核」流程。
- 交付 `artifacts/issueflow/ch04-security-audit.md`、`ch04-remediation.md` 與 `final-summary.md`，完成 5 分鐘 IssueFlow 垂直流程展示。

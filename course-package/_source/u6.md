# u6｜Spring AI ChatClient、SSE 與 tool calling

> 建立會即時串流回覆的 AI 對話助理，讓 AI 查 CRM 真實資料作答，並自動算出客戶風險等級、判讀每筆往來的情緒與意圖。

**時數**：09:00 ~ 12:00

**特色**：建立 Spring AI 對話入口，理解串流輸出、對話記憶與多 session 管理。、讓模型透過工具呼叫查詢即時資料或呼叫外部 API，而不是只依賴語料記憶作答。、使用 React 串接後端 Server-Sent Events (SSE) 串流 API，利用原生 EventSource 與狀態管理實現即時打字機對話效果。

## 學習目標
- 掌握 ChatClient 在 Spring AI 的使用位置
- 理解 SSE 串流輸出的呈現方式
- 知道如何以 sessionId 隔離不同使用者對話
- 理解 Tool Calling 與 Function Calling 的實際用途
- 分辨 `@Tool` 與 `ToolCallback` 的使用場景
- 掌握 AI 查詢資料庫的安全責任邊界
- 理解 SSE 與 WebSockets 的區別與選型
- 使用 React 的 EventSource 實作後端 API 串接
- 利用 React 狀態 (State) 實作流式打字渲染效果
- 掌握流式對話中對話 Session 的前端管理與清除

## 核心原則
可信任 AI 的界線是「數字由工具算，文字由模型寫」。我們透過 System Prompt 設定邊界，以 Tool Calling 將 CRM 動態領域資料提供給 LLM，並使用 SSE 串流將 token 即時渲染至聊天介面。

## 概念講解（concepts）

### AI CRM 助理的商業價值（分組：AI CRM 助理定位）
AI 助理不是「聊天機器人」，而是業務人員的智慧工作夥伴。在 CRM 場景中，AI 能創造三層價值：

**第一層：資訊查詢（Tool Calling）**
業務問「APIM 最近的合約狀況？」，AI 呼叫 CRM API 查詢客戶資料、商機與互動紀錄，整理成結構化摘要。省去業務人員在多個頁面間切換查找的時間。

**第二層：知識檢索（RAG）**
業務問「APIM 適合推薦哪個方案？」，AI 從向量化的產品文件與銷售話術中檢索相關內容，結合客戶的產業特性與需求給出推薦。

**第三層：洞察建議（結合 Tool Calling + RAG + 歷史記憶）**
業務問「GlobalMart 有流失風險嗎？該怎麼處理？」，AI 綜合分析：
- 合約即將到期（CRM 資料）
- 最近互動提及「預算凍結」與「競品比較」（歷史互動向量搜尋）
- 過去類似情境的成功挽留策略（知識庫 RAG）

最終產生具體的行動建議：「建議在 7 月 15 日前安排高層會議，提出客製化續約方案，重點強調...」

這就是 AI CRM 的核心價值：**讓每一位業務人員都擁有資深顧問級的分析能力**。

### ChatClient 核心概念（分組：ChatClient 基礎與對話記憶）
**ChatClient 在架構中的位置**

這一章開始，專案從純後端工程擴展到 AI 對話應用。`ChatClient` 是 Spring AI 2.0 中相對高階、可組合的入口，負責把使用者輸入、Advisor、Tools 與模型回應串成一條可讀的流程。

教學上可以把它想成客服總機。總機本身不處理所有問題，但它知道該把輸入送到哪裡、要不要帶記憶、要不要叫工具。

---

**串流輸出為什麼重要**

對使用者來說，串流輸出最大的價值不是技術炫耀，而是等待感受不同。模型可以一邊生成一邊顯示，前端不需要等整段文字全部完成才開始呈現。

在這個課程範例中，前端使用 SSE 讀取後端串流結果，這也為後面的 Demo 頁面奠定互動感。

---

**對話記憶設計**

- 不同使用者應對應不同 `sessionId`
- 記憶不應全站共用，否則會互相污染上下文
- 清除對話時應一併重建 session 識別值

### 工具呼叫核心概念（分組：Tool Calling 工具呼叫）
**工具呼叫的真正價值**

工具呼叫的本質，不是讓模型變強，而是讓模型不必假裝自己知道即時資料。它可以把需要查詢、計算或呼叫外部服務的工作交給可控工具處理。

對企業系統來說，這一點非常重要，因為真正的業務資料往往存在資料庫、內部 API 或受權限控制的服務中。

---

**@Tool 與 ToolCallback 的使用邏輯**

- `@Tool` 適合你自己在專案內部封裝的功能
- `ToolCallback` 適合掛接外部或唯讀工具
- 無論是哪一種，都應該透過既有 Service 邏輯取得資料
- 不要讓模型直接碰資料庫連線或繞過商業規則

### @Tool vs ToolCallback 選型原則（分組：Tool Calling 工具呼叫）
工具呼叫有兩種宣告方式，選擇依據是你是否有原始碼的修改權限。

- `@Tool` — 自己開發的業務方法，直接在方法上標註，最簡單
- `MethodToolCallback` — 第三方 JAR（無法加註解），用反射包裝現有方法
- `FunctionToolCallback` — 需要客製化邏輯的外部工具，用 Lambda + DTO 封裝
- 無論哪種方式，都應透過 Service 層取得資料，不讓模型直接碰資料庫連線

### 工具呼叫的架構定位（分組：Tool Calling 工具呼叫）
工具呼叫讓 AI 成為業務邏輯的「呼叫者」，而不是直接存取資料。不論工具背後是資料庫、內部 Service，還是第三方 API，模型看到的都是統一的工具介面。

這種設計讓後端的資料來源可以隨時替換或擴充，而不影響模型的呼叫方式。

### 為什麼選擇 SSE (Server-Sent Events)（分組：SSE 前端串流整合）
在 AI 聊天應用中，模型的回應是單向且持續產生的，後端需要持續把資料推給前端，而前端不需要在過程中頻繁向後端傳送資料。

相較於 WebSockets 的雙向複雜協定，SSE 是基於標準 HTTP 的單向推播協定，開發簡單、開銷小，且天生支援斷線重連。Spring AI 的 `.stream()` 預設就是輸出標準的 `text/event-stream` 格式，與 SSE 完美搭配。

- WebSockets：雙向通道，適用於多人遊戲、協作工具，但協定較為繁重。
- SSE (Server-Sent Events)：單向推送，基於 HTTP，最適合大模型流式生成 (Streaming)。
- React 連線方式：使用瀏覽器內建的 `EventSource` 物件即可建立連線，不需要引入第三方 WebSocket 庫。

### AI Agent 提示詞 — 前端串流與安全認證（分組：SSE 前端串流整合）


使用者詢問特定客戶的銷售進度時（例如「亞太智能製造有哪些進行中的生意機會？」），AI 精確識別客戶名稱並呼叫 OpportunityTools 商機查詢工具，回傳對應的銷售機會。前端會將其渲染出包含商機名稱、金額、成交機率與銷售階段的卡片。

### 系統運行展示：長期記憶語意客戶推薦（分組：系統運行展示）
當使用者點擊「長期記憶語意推薦」時，後端啟動雙路 RAG 檢索，同時在 pgvector 中查找此使用者在過去幾天內聊過的客戶偏好與銷售重點（例如曾提及專注於製造業、偏好金額大的案子、對特定合作案感興趣等）。AI 結合記憶推薦 CRM 中的特定客戶或機會，前端渲染出極具說服力的語意推薦卡片與推薦理由。

### ① 加上一個會聊天的 AI 智慧助手［build］
> Groq 端點、SSE 逐字串流、sessionId 記憶、每次呼叫記 ai_call_log
```text
請幫這套系統加上一個 AI 智慧助手（Spring AI 2.0.x 的 ChatClient），讓我可以用「聊天」的方式問跟客戶有關的問題。模型端點走 Groq 的 OpenAI 相容 API（base-url https://api.groq.com/openai，模型 openai/gpt-oss-120b），金鑰從環境變數 GROQ_API_KEY 讀取，不要寫死在程式碼中。系統提示詞：「你是一個親切的 CRM 智慧助手，只根據系統提供的資料回答，資料不足就明說，不要編造金額或日期」。回答要像打字一樣一個字一個字即時跳出來（SSE 串流，端點 GET /api/ai/stream），而且不同使用者的對話要各自分開記住、不會混在一起（用 MessageChatMemoryAdvisor，記憶 key 用 sessionId，並以登入者身分綁定 sessionId，別人不能用別人的）。每一次呼叫都要記一筆 ai_call_log（呼叫類型、客戶、模型、token 用量、回答摘要、時間），之後第七章要拿來查歷史。請加繁體中文註解。
```

### ② 讓 AI 回答前先查真實資料、不要亂編［build］
> Tool Calling 包既有 Service，只讀、套權限、遮罩個資
```text
請讓這個 AI 助手在回答前，會先去查資料庫裡的真實資料，而不是自己想像：用 Spring AI 的 Tool Calling，把既有 Service 包成工具給模型用——CustomerTools（依關鍵字查客戶清單、依 id 查客戶詳情含風險等級）與 OpportunityTools（查某客戶的生意機會、查某筆生意的金額與階段），每個工具的 description 用中文寫清楚「什麼情況該呼叫」；工具只讀不寫，而且要套用登入者的權限（SALES 只能查到自己負責的客戶）。送給模型的資料要先把 email、電話、統編遮罩。比如我問「環球零售巨擘的生意進度如何」，它要先去撈出那個客戶真正的資料和數字，再根據真實資料回答；問一個不存在的客戶，要回「查無此客戶」而不是編故事。請加繁體中文註解，並告訴我怎麼從後端日誌看到工具真的被呼叫。
```

### ③ 在網頁上做出 AI 聊天室［build］
> 即時打字效果，而且要確認是已登入的人
```text
請在網頁上做一個 AI 聊天室（放在客戶詳情頁的側欄，也能從導覽列打開），連上剛才的助手，要有訊息即時一個字一個字跳出來的效果：前端用 EventSource 連 /api/ai/stream?message=…&sessionId=…&token=…，把 localStorage 的 JWT 用網址參數帶上；後端的 JwtAuthenticationFilter 除了 Authorization 標頭，也要能從 token 這個網址參數驗證，確保只有「已經登入的人」才能使用這個聊天，外人不能亂用。畫面要有送出中的骨架屏、錯誤提示、清除對話（清除時換一個新的 sessionId）。畫面設計請用 uiuxpromax 技能來決定風格、配色與載入／錯誤／沒資料時的呈現，和已經做好的頁面保持一致。請加繁體中文註解。
```

### ④ 一鍵產生「客戶 AI 評估報告」［build］
> 結訓必做；報告數字一定要來自真實資料
```text
請加一個「客戶 AI 評估」功能（GET /api/ai/customers/{id}/assessment，同時提供一般回應與 SSE 串流版）：我選一個客戶，後端先把他的基本資料、最近的往來紀錄、進行中的生意、程式算好的風險等級整理成事實清單交給模型，AI 依固定四段輸出 Markdown 報告：「健康度總評」、「生意機會分析」、「風險與預警」、「建議的下一步行動」。報告裡出現的數字一定要來自事實清單，不可以自己編造；報告要存成一筆 ai_call_log，並把報告呈現在客戶詳情頁裡（一個按鈕產生、彈出視窗顯示，可看上一次的報告）。請加繁體中文註解。
```

### ⑤ 自動算出每個客戶的風險等級［build］
> 60 / 30 天規則由程式算，存欄位、每日重算、可篩選
```text
請幫每一個客戶自動算出一個「風險等級」（HIGH 高 / MEDIUM 中 / LOW 低），規則由程式算、不要交給 AI 猜：距離最近一次往來超過 60 天、或預計續約日已經過了 → HIGH；超過 30 天 → MEDIUM；完全沒有往來紀錄 → MEDIUM；其餘 → LOW。結果存在客戶的 risk_level 與 risk_computed_at 欄位（用 Flyway 新增），每天凌晨重算一次、新增往來紀錄時也即時重算；客戶清單要能用 riskLevel 篩選，清單與詳情頁要用顏色標籤清楚標示；而且前面做的 AI 評估和聊天回答（CustomerTools 的詳情）也要把它考慮進去。請加繁體中文註解。
```

### ⑥ 自動判讀每筆往來的情緒與意圖［build］
> 固定的情緒與意圖標籤，存 interaction_insights，做情緒總覽
```text
請讓系統自動判讀每一筆客戶往來紀錄的「情緒」（POSITIVE 正面 / NEUTRAL 中性 / NEGATIVE 負面，附 -100～100 的分數）和「意圖」（ASK_PRICING 詢價、COMPARE_COMPETITOR 比較競品、CHURN_SIGNAL 有想離開的跡象、RENEWAL_INTEREST 想續約、UPSELL_SIGNAL 想加購、COMPLAINT 客訴、OTHER 其他）：新增往來紀錄時就呼叫模型判讀一次，結果存在 interaction_insights 表（用 Flyway 新增），既有的紀錄在啟動時補算。然後在儀表板做一個情緒總覽（GET /api/dashboard/sentiment）：近期負面互動最多的客戶、出現 CHURN_SIGNAL 或 COMPARE_COMPETITOR 的客戶，特別標出最近有流失風險、需要優先關心的客戶。往來紀錄清單上也要顯示每筆的情緒與意圖標籤。請加繁體中文註解。
```

### ✅ 驗證 — AI 講的數字是真的，洞察有在運作［verify］
> 數字相符、有風險提醒、有情緒判讀
```text
請幫我驗證幾件事：問「亞太智能製造目前有哪些進行中的生意？金額多少？」，AI 回答的金額（1,200,000）、階段、往來次數要跟資料庫一致，後端日誌要看得到工具被呼叫；問一個資料庫裡不存在的客戶，AI 要回查無資料；用兩個不同帳號各聊各的，記憶不能互相看到；對鼎峰金融科技做 AI 評估，要看到明顯的風險提醒且風險等級是 HIGH；環球零售巨擘那封提到預算凍結的 Email 情緒要是 NEGATIVE、意圖要是 COMPARE_COMPETITOR 或 CHURN_SIGNAL；並確認 ai_call_log 有這幾次呼叫的紀錄。
```

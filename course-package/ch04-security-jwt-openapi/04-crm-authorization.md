# 章節 4 單元 4｜CRM 的權限設計

## 單元定位

單元 3 用 ADMIN / USER 兩種角色打好認證授權的地基；本節把它升級成 AI CRM 主軸專案真正需要的權限模型：SALES / MANAGER / ADMIN 三種角色，以及「API 層、資料層、AI 層」三層權限控制——特別是 AI 層，這是傳統權限設計沒有、卻是 AI 應用上線前必須想清楚的一層。本節偏設計思維，為第六、七章的 AI 助理與 RAG 知識庫預埋權限邊界。建議時長：15～20 分鐘。

## 教學素材

### CRM 角色與權限模型

AI CRM 系統的角色設計反映真實企業的組織層級：

**ROLE_SALES（業務人員）**
- 可查看/編輯自己負責的客戶、商機與互動紀錄。
- 可使用 AI 助理進行客戶分析與行動建議。
- 不可查看其他業務人員的客戶資料。

**ROLE_MANAGER（業務主管）**
- 可查看團隊內所有業務人員的客戶與商機。
- 可查看團隊的銷售報表與 AI 預測分析。
- 可指派任務給業務人員。

**ROLE_ADMIN（系統管理員）**
- 可管理使用者帳號、角色與權限。
- 可管理 RAG 知識庫（上傳/刪除產品文件、銷售話術）。
- 可查看系統日誌與 AI 使用統計。

### 權限控制實作要點：三層防線

- **API 層**：用 `@PreAuthorize` 標註控制端點存取。
- **資料層**：用 Specification 自動加入 `salesRepId` 過濾條件——業務即使呼叫「查詢所有客戶」，查出來的也只有自己負責的客戶。
- **AI 層**：工具呼叫自動注入當前使用者的權限範圍，確保 AI 不會洩露跨業務的客戶資料。

三層缺一不可：只做 API 層，業務仍能透過查詢端點看到全部客戶；只做前兩層，AI 助理的 Tool Calling 仍可能替使用者「代查」他無權看的資料。

## 示範與提示詞

本節以設計討論為主，實作驗證沿用本章 prompts 的「✅ 驗證 — 在操作說明頁跑一次權限流程」：

```text
請帶我在那個線上操作說明頁上驗證權限：先登入拿到通行身分，接著用一般使用者的身分試著刪客戶（應該被擋），再換成管理員重試（應該成功），確認權限控管和錯誤訊息都跟預期一樣。
```

驗證重點：一般身分刪客戶收到 403（且錯誤訊息是單元 2 統一格式）、管理員刪除成功；同時對照三角色模型，口頭盤點每個角色在 API 層 / 資料層 / AI 層各自能碰到什麼。

## 口語稿

上一節結尾我留了一個問題：ADMIN 和 USER 兩種角色，夠用嗎？對一個教學範例夠了，但對真實的 CRM 系統，差得遠。你想想一家公司的業務部門：業務人員、業務主管、系統管理員，這三種人對客戶資料的需求完全不一樣。這一節我們不急著寫程式，先把 AI CRM 的權限模型想清楚——設計想錯了，後面寫再多程式都是白工。

我們的角色設計直接反映真實企業的組織層級，三個角色。第一個，ROLE_SALES，業務人員。他可以查看和編輯「自己負責的」客戶、商機和互動紀錄，也可以使用 AI 助理做客戶分析、拿行動建議。但注意那個關鍵限制：他不可以看到其他業務的客戶資料。為什麼這條這麼重要？因為業務的客戶名單就是他的飯碗，也是公司的商業機密，業務之間互看名單在真實企業是很敏感的事。第二個，ROLE_MANAGER，業務主管。他可以看團隊內所有業務的客戶和商機、看團隊的銷售報表和 AI 預測分析，還可以指派任務給業務。第三個，ROLE_ADMIN，系統管理員。他管的是系統本身：使用者帳號和角色權限、RAG 知識庫的文件上傳與刪除——這個第七章會用到——還有系統日誌和 AI 使用統計。

角色定義好了，接下來是這一節真正的重點：權限要在「哪幾層」落實？答案是三層，缺一不可。第一層，API 層，用 @PreAuthorize 標註控制哪些端點誰能呼叫，這就是上一節做的事情的延伸。但你馬上會發現只有這層不夠——「查詢客戶」這個端點業務本來就能呼叫，可是他呼叫之後，不能查到別人的客戶啊。所以需要第二層，資料層：還記得第三章學的 Specification 動態查詢嗎？我們讓它自動加入 salesRepId 的過濾條件，業務就算呼叫「查詢所有客戶」，資料庫吐回來的也只有他自己負責的那些。權限不是擋在門口就好，還要過濾到資料本身。

然後是第三層，AI 層——這一層是傳統系統沒有的，也是我特別想讓你記住的。第六章我們會讓 AI 助理透過 Tool Calling 去讀真實的 CRM 資料。你想像一個情境：業務小王問 AI「幫我分析一下客戶陳先生的狀況」，但陳先生是業務小李的客戶。如果 AI 的工具呼叫沒有權限概念，它就會乖乖去資料庫把陳先生的資料查出來、整理得漂漂亮亮告訴小王——你的 API 層和資料層防得再好,都被 AI 從旁邊繞過去了。所以做法是：工具呼叫的時候，自動注入當前使用者的權限範圍，AI 查資料永遠是「以這個使用者的身分」在查，確保 AI 不會洩露跨業務的客戶資料。一句話總結這三層：API 層管「這個門你能不能進」，資料層管「進來之後你看得到哪些資料」，AI 層管「你請 AI 代辦的時候，AI 不能比你看得更多」。

我們現在來收尾驗證一下。回到 Swagger 操作說明頁，把權限流程完整跑一遍：先登入拿到通行身分，用一般使用者的身分試著刪客戶——你會看到被 403 擋下來，而且錯誤訊息是我們單元 2 做的統一格式，看得懂、不嚇人；換成管理員重試，刪除成功。然後對照三角色模型，在心裡盤點一次：SALES 在三層各碰得到什麼、MANAGER 多了什麼、ADMIN 又多了什麼。

總結一句：權限設計不是「加個登入」而已，而是 API、資料、AI 三層一起守，其中 AI 層是智慧應用時代的新考題，我們在第六章實作工具呼叫時會真正把它做出來。到這裡，第四章的內容就完整了——文件、錯誤處理、認證授權、權限模型，你的客戶 API 已經是一個「能上線」的樣子。接下來是本章作業：親手為 AI CRM 加上權限控管，我們作業說明見。

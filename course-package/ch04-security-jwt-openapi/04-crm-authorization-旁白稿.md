# 04-crm-authorization｜CRM 的權限設計旁白稿

本稿依據 `04-crm-authorization.md` 的教學素材與口語稿整理，供人工錄音使用。共 6 段，錄音時可依段落分開保存，方便後續與投影片時間軸對齊。

建議錄音格式：WAV 或 MP3。每段開頭保持自然，結尾保留約 0.5 秒空白。

## 01｜兩種角色夠用嗎

建議檔名：`01-two-roles-enough.wav`

上一節結尾我留了一個問題：ADMIN 和 USER 兩種角色，夠用嗎？對一個教學範例夠了，但對真實的 CRM 系統，差得遠。你想想一家公司的業務部門：業務人員、業務主管、系統管理員，這三種人對客戶資料的需求完全不一樣。這一節我們不急著寫程式，先把 AI CRM 的權限模型想清楚——這也是這門課一貫的做法：先懂設計，再讓 AI 動手。設計想錯了，後面寫再多程式都是白工。

## 02｜三個角色的設計

建議檔名：`02-three-roles.wav`

我們的角色設計直接反映真實企業的組織層級，三個角色。第一個，ROLE_SALES，業務人員。他可以查看和編輯「自己負責的」客戶、商機和互動紀錄，也可以使用 AI 助理做客戶分析、拿行動建議。但注意那個關鍵限制：他不可以看到其他業務的客戶資料。為什麼這條這麼重要？因為業務的客戶名單就是他的飯碗，也是公司的商業機密。第二個，ROLE_MANAGER，業務主管。他可以看團隊內所有業務的客戶和商機、看銷售報表和 AI 預測分析，還可以指派任務。第三個，ROLE_ADMIN，系統管理員。他管的是系統本身：使用者帳號和角色權限、RAG 知識庫的文件上傳與刪除——這個第七章會用到——還有系統日誌和 AI 使用統計。

## 03｜API 層與資料層

建議檔名：`03-api-and-data-layer.wav`

角色定義好了，接下來是這一節真正的重點：權限要在「哪幾層」落實？答案是三層，缺一不可。第一層，API 層，用 @PreAuthorize 標註控制哪些端點誰能呼叫，這是上一節做的事情的延伸。但你馬上會發現只有這層不夠——「查詢客戶」這個端點業務本來就能呼叫，可是他呼叫之後，不能查到別人的客戶啊。所以需要第二層，資料層：還記得第三章學的 Specification 動態查詢嗎？我們讓它自動加入 salesRepId 的過濾條件，業務就算呼叫「查詢所有客戶」，資料庫吐回來的也只有他自己負責的那些。權限不是擋在門口就好，還要過濾到資料本身。

## 04｜AI 層：智慧應用的新考題

建議檔名：`04-ai-layer.wav`

然後是第三層，AI 層——這一層是傳統系統沒有的，也是我特別想讓你記住的。第六章我們會讓 AI 助理透過 Tool Calling 去讀真實的 CRM 資料。你想像一個情境：業務小王問 AI「幫我分析一下客戶陳先生的狀況」，但陳先生是業務小李的客戶。如果 AI 的工具呼叫沒有權限概念，它就會乖乖去資料庫把陳先生的資料查出來、整理得漂漂亮亮告訴小王——你的 API 層和資料層防得再好，都被 AI 從旁邊繞過去了。所以做法是：工具呼叫的時候，自動注入當前使用者的權限範圍，AI 查資料永遠是「以這個使用者的身分」在查。一句話總結這三層：API 層管「這個門你能不能進」，資料層管「進來之後你看得到哪些資料」，AI 層管「你請 AI 代辦的時候，AI 不能比你看得更多」。

## 05｜把權限流程跑一遍

建議檔名：`05-verify-flow.wav`

我們現在來收尾驗證一下。回到 Swagger UI，把權限流程完整跑一遍：先登入拿到通行身分，用一般使用者的身分試著刪客戶——你會看到被 403 擋下來，而且錯誤訊息是我們單元 2 做的統一格式，看得懂、不嚇人；換成管理員重試，刪除成功。驗證用的提示詞在教學網站上，照著跑就好。然後對照三角色模型，在心裡盤點一次：SALES 在三層各碰得到什麼、MANAGER 多了什麼、ADMIN 又多了什麼。

## 06｜第四章總結與下一章預告

建議檔名：`06-closing.wav`

總結一句：權限設計不是「加個登入」而已，而是 API、資料、AI 三層一起守，其中 AI 層是智慧應用時代的新考題，我們在第六章實作工具呼叫時會真正把它做出來。到這裡，第四章就完整了——文件、錯誤處理、認證授權、權限模型，你的客戶 API 已經是一個「能上線」的樣子。接下來是本章作業：親手為 AI CRM 加上權限控管。做完作業之後，下一章我們就要換到瀏覽器這一端，用 React 打造前端工作台，把這套 API 真正變成使用者看得到、點得動的畫面。我們下一章見。

## 邊念邊操作提示卡

1. 先顯示角色矩陣，逐列念 ADMIN、MANAGER、SALES、VIEWER 對 customer、opportunity、interaction 的操作權。
2. 使用不同 token 呼叫同一 endpoint；每一次停在 status 和 body，接著示範同角色操作另一位負責人的資料。
3. 打開 service authorization test，指出後端規則不能只靠前端隱藏按鈕；log 只展示 actor、resource 和 decision。
4. 結尾把矩陣與拒絕案例存檔，說明 React 會沿用這份契約，但仍以後端為準。

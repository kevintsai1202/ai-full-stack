# 章節 5 單元 4｜CRM 工作台設計思維

## 單元定位

專案骨架、JSX 能力、視覺樣式都備齊了，本單元是章節 5 的收斂點：從業務人員的日常工作流出發，設計 CRM 工作台的核心頁面（Dashboard、客戶列表、客戶詳情、商機看板、AI 助理入口），實作 API client 與 JWT 儲存自動帶 Token，並把登入與真實後端資料接起來——驗證重點是「能登入並查到真實後端資料」。本單元完成後即可進行本章作業；下一章（章節 6）將把 Spring AI 的對話能力接進這個工作台。建議時長：14～16 分鐘。

## 教學素材

### 前後端整合的核心原則

前後端整合的核心在於狀態的一致性與防禦性渲染。Axios Interceptor 可以自動為請求附加 JWT，並在 401 時引導重新登入；UI 上必須對 Loading、Error 及 Empty 進行完整處理，保障使用者體驗。（對應素材 mat6：「React 與 Axios 前後端整合說明」——React 19 呼叫後端 API、JWT 自動攜帶與 Axios 攔截器 (Interceptors) 設計說明。）

### CRM 工作台的核心畫面

CRM 前端工作台的核心畫面設計，圍繞業務人員的日常工作流：

**Dashboard（儀表板）**
展示關鍵指標：本月商機總額、待跟進客戶數、即將到期合約、AI 建議的優先行動。使用卡片式佈局，數據來自後端 API 的即時聚合。

**Customer List（客戶列表）**
支援動態篩選（產業、合約狀態、最後互動時間）與搜尋。列表使用虛擬滾動處理大量資料，點擊進入客戶詳細頁面。

**Opportunity Board（商機看板）**
看板式佈局（類似 Trello），每個欄位代表商機階段（Prospecting → Qualification → Proposal → Closing）。可拖拽商機卡片變更階段。

**AI Chat（AI 助理）**
右側浮動面板或獨立頁面，支援 SSE 串流對話、Markdown 渲染、客戶摘要卡片與行動建議按鈕。（本章先留好入口，功能在章節 6 實作。）

### 元件設計原則

- 每個頁面是一個 Route，共用 Layout 元件（側欄 + 頂部導覽）。
- 資料請求統一用 Axios + Vite Proxy。
- CSS 使用 HSL 色彩系統，支援深色/淺色主題切換。

### 儀表板的分析深化與客戶分群

總覽儀表板可再往上做成有分析價值的經營儀表板：生意機會各階段漏斗圖、未來幾個月的營收預測、各產業營收分布、客戶風險分布、快到期該續約的客戶、業務績效排行榜、最近往來活動——且每張圖點下去要能看到背後的客戶或生意明細（下鑽）。另可加上「該優先追哪些客戶」的分群：依「多久沒聯絡了」、「往來頻繁程度」、「生意金額大小」三個面向自動評分貼標，給出「重點客戶」、「有潛力」、「需要喚醒」等分群標籤。

## 示範與提示詞

### ② 讓網頁接上後端並記住登入

```text
請幫網頁接上後端：做一個登入頁呼叫 POST /api/auth/login，登入成功後把 token 與使用者資訊存在瀏覽器（localStorage），之後每次呼叫 API 都用 axios 攔截器自動帶上 Authorization: Bearer；用一個 AuthContext 讓所有頁面都知道目前登入的人與角色；沒登入的人開任何頁面都導回 /login；如果 API 回 401（登入過期），就自動清掉 token 並把我導回登入頁重新登入。側欄的「團隊分析」只有 MANAGER 與 ADMIN 看得到。請加繁體中文註解。
```

### ③ 做出 CRM 的核心頁面並接上真實資料

```text
請做出 CRM 的幾個主要頁面，並接上後端的真實資料：登入頁；總覽儀表板（先放幾張重要數字卡片：客戶數、進行中生意機會數與總金額、本月新增往來數，資料來自 GET /api/dashboard/summary）；客戶清單（可以用關鍵字、產業、狀態、負責業務搜尋與篩選，有分頁，接 GET /api/customers 的 items 分頁格式）；客戶詳情（網址用 /customers/:id，分頁切換看聯絡人 / 往來紀錄 / 生意機會，可在頁上新增聯絡人與往來紀錄）；以及生意機會看板（依 QUALIFICATION → PROPOSAL → NEGOTIATION → CLOSED_WON / CLOSED_LOST 分欄排列，拖拉卡片就呼叫更新階段的 API，失敗要退回原欄）。沒登入要導回登入頁，載入中 / 載入失敗 / 沒有資料時都要有清楚的畫面。生意機會看板請用後端已經有的「全公司生意機會清單」來做。除了總覽用的 GET /api/dashboard/summary，後端不要自己再新增其他功能；如果做到一半發現前端還缺什麼後端功能，先停下來列給我看，因為新功能要先回第四章的權限表補一列再做。畫面設計請用 uiuxpromax 技能來決定風格、配色與載入／錯誤／沒資料時的呈現，和已經做好的頁面保持一致。請加繁體中文註解。
```

### ⑤ 加上「該優先追哪些客戶」的分群

```text
請在儀表板加一個「該優先追哪些客戶」的功能（RFM 分群）：後端新增 GET /api/dashboard/rfm，依照三個面向幫每個客戶各打 1～5 分——「多久沒聯絡了」（最近一次往來距今天數，越近分越高）、「平常往來頻不頻繁」（近 90 天往來次數）、「生意金額大不大」（進行中與已成交的生意金額總和）。然後依分數組合貼上分群標籤：三項都高是「重點客戶」、最近有聯絡但金額還小是「有潛力」、金額大但很久沒聯絡是「需要喚醒」、其餘是「需關注」，讓我一眼就知道該先追誰。前端做成一張可排序的表，顯示三個分數與標籤。畫面設計請用 uiuxpromax 技能來決定風格、配色與載入／錯誤／沒資料時的呈現，和已經做好的頁面保持一致。請加繁體中文註解。
```

### ✅ 驗證 — 各頁面與圖表都是真實資料

```text
請幫我做一次完整確認：用 sales 帳號登入後，總覽的數字、各張分析圖表、客戶清單和詳情顯示的都是後端來的真實資料（拿亞太智能製造的生意機會金額 1,200,000 跟畫面對一次）；點圖表能看到背後的明細；客戶分群標籤有正常顯示（鼎峰金融科技應該是「需要喚醒」）；用 sales 登入看不到團隊分析、換 manager 看得到；登出或登入過期會回到登入頁。請把這個流程寫成 Playwright 腳本放在 frontend/e2e/，讓我之後可以重跑。
```

## 逐步操作與驗收

### 依業務工作流組裝工作台

1. 先列出 Dashboard、Customer List、Customer Detail、Opportunity Board、AI Chat 五個入口，再為每個入口寫資料來源、主要操作、Loading/Error/Empty 狀態與權限。
2. 建立共用 Layout、route 與 API client；以 Axios interceptor 自動帶 JWT，遇到 401 清除 session 並導回登入，不能讓每個元件各自複製邏輯。
3. 先用真實後端資料完成登入、客戶清單搜尋與詳情，再接 dashboard 聚合和 opportunity 看板；每接一個頁面就保存 Network request/response。
4. 用測試帳號檢查不同角色的入口、錯誤 API、空資料與 token 過期；圖表下鑽必須能回到具體客戶或商機，而不是只顯示漂亮數字。

### 預期結果與證據

- 測試帳號能登入並查到真實資料，401 能回登入頁；五個入口有明確 route，三態與權限行為可重現。
- 交付頁面地圖、API client、登入前後 Network、角色差異、圖表下鑽與空/錯誤畫面證據。

### 失敗分流與銜接

- CORS/proxy 失敗先看瀏覽器 Network 與 Vite log；資料顯示假數字時追查 API response 和 mapping；token 遺失時檢查儲存與 interceptor。
- 下一章會在 AI Chat 入口加入 SSE、tool calling 與記憶，先確保工作台能安全呈現真實後端資料。

## 口語稿

前面三節，工具都到位了：專案跑得起來、JSX 看得懂、視覺樣式也調好了。這一節是本章的重頭戲——我們要把 CRM 工作台真正組裝起來，接上前四章做好的後端。開始寫提示詞之前，先想一個問題：業務人員一天的工作長什麼樣？早上打開系統，先看今天該做什麼；然後查某個客戶的狀況；追蹤手上的生意進行到哪個階段。頁面設計不是我們想放什麼就放什麼，而是跟著這個工作流走。

照這個思路，工作台有四個核心畫面。第一個是 Dashboard 儀表板，開門見山展示關鍵指標：本月商機總額、待跟進客戶數、即將到期的合約、還有 AI 建議的優先行動。用卡片式佈局，而且每個數字都來自後端 API 的即時聚合——不是寫死的假數字。第二個是客戶列表，要能搜尋、能依產業、合約狀態、最後互動時間動態篩選，資料量大的時候用虛擬滾動處理，點一列就進入客戶詳情頁。第三個是商機看板，長得像 Trello：每個直欄代表一個商機階段，從 Prospecting、Qualification、Proposal 到 Closing，卡片可以拖拽換欄，換欄就等於更新這筆生意的階段。第四個是 AI 助理，做成右側浮動面板或獨立頁面，支援 SSE 串流對話跟 Markdown 渲染——這個入口我們這一章先留好位置，功能下一章接 Spring AI 的時候實作。

架構上有三條元件設計原則。第一，每個頁面是一個 Route，共用一個 Layout 元件，側欄加頂部導覽，換頁的時候只換中間的內容區。第二，資料請求統一用 Axios 搭配我們第一節設好的 Vite Proxy，所有請求走同一個出口。第三，CSS 用 HSL 色彩系統，方便支援深色淺色主題切換。

接著是本章技術上最關鍵的一塊：登入狀態怎麼管。回想第四章，後端所有 API 都被 JWT 保護著，前端每一次請求都得帶 Token。難道每支查詢函式都手動塞一次 header 嗎？當然不行。答案是 Axios Interceptor，攔截器。它就像 API client 的關卡：請求出去之前，攔截器自動把儲存好的 JWT 附加到 header 上；回應進來的時候，如果後端回 401，代表 Token 過期或無效，攔截器就自動把使用者導回登入頁。這樣「帶 Token」跟「處理過期」這兩件事只要寫在一個地方，所有請求自動受惠。我們現在來用第二段提示詞把這件事交給 AI：「登入成功後自動記住我的身分，之後每次操作都自動帶著；登入過期就自動導回登入頁」——你會看到 AI 做出登入流程、把 Token 存下來，然後建出攔截器。

再來用第三段提示詞把核心頁面一次做出來：登入頁、總覽儀表板放幾張數字卡片、可搜尋篩選的客戶清單、分頁切換聯絡人／往來紀錄／生意機會的客戶詳情，還有依階段分欄的商機看板。注意提示詞裡有兩個防禦性要求：沒登入要導回登入頁；載入中、載入失敗、沒有資料三種狀態都要有清楚的畫面——上一節講的骨架屏，這裡就派上用場了。

如果你想把儀表板做得更有分析價值，第四段提示詞可以加上漏斗圖、營收預測、產業分布、風險分布、續約提醒、業績排行榜這些經營圖表，而且要求每張圖點下去能下鑽看到背後是哪些客戶哪些生意；第五段提示詞再加一個客戶分群功能，依「多久沒聯絡」、「往來頻率」、「金額大小」三個面向自動評分貼標，分出重點客戶、有潛力、需要喚醒，讓業務一眼知道該先追誰。

最後，也是本章的驗收重點：用測試帳號實際登入一次。你會看到儀表板的數字、客戶清單、詳情頁顯示的通通是後端資料庫裡的真實資料，不是前端寫死的；點圖表能看到明細；登出或 Token 過期會乖乖回到登入頁。能走完這一圈，前後端就是真的接通了。

總結一下：這一節我們以業務工作流為軸設計了四大頁面，用 Axios Interceptor 解決 JWT 自動攜帶與 401 導回登入，並且驗證了工作台跑的是真實後端資料。接下來的作業，就是請你把這套前端基本架構完整做出來；而下一章，我們要讓這個工作台真正「智慧」起來——用 Spring AI 的 ChatClient 跟 SSE 串流，把 AI 助理接進來。

（口語稿約 1610 字）

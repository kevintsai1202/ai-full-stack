# 章節 6 單元 2｜工具呼叫

## 單元定位

本節要解決的問題：讓 AI 助理回答前先查 CRM 的真實資料，而不是依賴語料記憶瞎編——用 Tool Calling 把既有 Service 包裝成 AI 可呼叫的工具，並釐清 `@Tool` 與 `ToolCallback` 的選型原則與安全責任邊界。

與前後節的銜接：上一節建好 ChatClient 對話入口與記憶，但 AI 還查不到資料庫；本節讓它成為業務邏輯的「呼叫者」。下一節（單元 3）再把回覆用 SSE 串流到 React 前端。

建議時長：30 ～ 35 分鐘。

## 教學素材

### 工具呼叫的真正價值

工具呼叫的本質，不是讓模型變強，而是讓模型不必假裝自己知道即時資料。它可以把需要查詢、計算或呼叫外部服務的工作交給可控工具處理。對企業系統來說這一點非常重要，因為真正的業務資料往往存在資料庫、內部 API 或受權限控制的服務中。

### @Tool 與 ToolCallback 的使用邏輯

- `@Tool` 適合你自己在專案內部封裝的功能。
- `ToolCallback` 適合掛接外部或唯讀工具。
- 無論是哪一種，都應該透過既有 Service 邏輯取得資料。
- 不要讓模型直接碰資料庫連線或繞過商業規則。

### @Tool vs ToolCallback 選型原則

選擇依據是你是否有原始碼的修改權限：

- `@Tool` — 自己開發的業務方法，直接在方法上標註，最簡單。
- `MethodToolCallback` — 第三方 JAR（無法加註解），用反射包裝現有方法。
- `FunctionToolCallback` — 需要客製化邏輯的外部工具，用 Lambda + DTO 封裝。
- 無論哪種方式，都應透過 Service 層取得資料，不讓模型直接碰資料庫連線。

### 工具呼叫的架構定位

工具呼叫讓 AI 成為業務邏輯的「呼叫者」，而不是直接存取資料。不論工具背後是資料庫、內部 Service，還是第三方 API，模型看到的都是統一的工具介面。這種設計讓後端的資料來源可以隨時替換或擴充，而不影響模型的呼叫方式。

### 系統運行展示（工具呼叫實際效果）

- 客戶資訊查詢卡片：使用者詢問「有哪些客戶」時，後端 AI 模型自動呼叫 CustomerTools 客戶查詢工具，從 JPA 資料庫取得最新的客戶資料與等級資訊。
- 商機與銷售進度查詢：使用者詢問「台積電有哪些進行中的商機？」，AI 精確識別客戶名稱並呼叫 OpportunityTools 商機查詢工具，回傳對應的銷售機會（商機名稱、金額、成交機率與銷售階段）。

## 示範與提示詞

### AI Agent 提示詞 — 加入工具呼叫能力

```text
請為 CRM AI 助手加入工具呼叫（Tool Calling）能力，讓 AI 能查詢資料庫的即時資料：
1. 建立 CustomerTools 類別，用 @Tool 註解包裝既有的 CustomerService：
   - getCustomers(query)：查詢客戶列表，支援關鍵字搜尋，query 為空時回傳全部客戶
   - getCustomerDetail(id)：依客戶 ID 查詢詳細資訊（等級、產業、聯絡方式）
2. 建立 OpportunityTools 類別，用 @Tool 包裝既有的 OpportunityService：
   - getOpportunities(customerId)：查詢指定客戶的所有銷售機會
   - getDealValue(opportunityId)：查詢特定銷售機會的金額與成交機率
3. 每個 @Tool 的 description 請用中文清楚描述「什麼情況下該呼叫這個工具」，這段文字是寫給大模型看的。
4. 在 ChatController 的 ChatClient 呼叫鏈中，用 .tools() 掛上這兩個工具類別。
完成後請示範一句測試提問（例如「台積電目前的客戶等級是什麼？有哪些進行中的銷售機會？」），並說明如何從後端日誌確認工具真的被呼叫。
```

### 口語化建置提示詞 ②｜讓 AI 回答前先查真實資料、不要亂編

> AI 要去撈資料庫的真數字來回答

```text
請讓這個 AI 助手在回答前，會先去查資料庫裡的真實資料，而不是自己想像。比如我問「某個客戶的生意進度如何」，它要先去撈出那個客戶真正的資料和數字，再根據真實資料回答。請加中文註解。
```

## 口語稿

上一節結束的時候我留了一個坑：我們的 AI 助理會聊天、有記憶，但你問它「台積電的商機金額多少」，它會很有自信地給你一個數字——一個編出來的數字。這就是這一節要解決的問題。為什麼模型會編？因為大語言模型的知識來自訓練語料，你資料庫裡的客戶資料它從來沒看過，但它的天性是「一定要給你一個答案」。企業系統最怕的就是這種一本正經的胡說八道。

解法叫 Tool Calling，工具呼叫。這裡我要先糾正一個常見的誤解：工具呼叫的本質，不是讓模型變強，而是讓模型「不必假裝自己知道」。我們把查詢、計算、呼叫外部服務這些工作，交給可控的工具去處理，模型只負責決定什麼時候該用哪個工具、以及把工具回傳的結果整理成人話。聽出來了嗎？這正是我們的口訣——數字由工具算、文字由模型寫。工具撈出來的金額、次數、等級是精確的，模型負責把它們串成一段好讀的回答；如果工具查不到資料，那就老實說查無資料，不亂答。

那流程實際上是怎麼跑的？你把工具的名稱、參數跟描述註冊給模型，模型收到問題後如果判斷需要即時資料，它不會直接回答，而是回傳「我要呼叫某某工具、參數是什麼」；Spring AI 幫你執行那個工具，把結果再送回給模型，模型才根據真實資料組出最終回答。整個過程中，模型從頭到尾沒有碰你的資料庫，它只是一個「呼叫者」。

Spring AI 裡宣告工具有兩條路，選型原則很簡單：看你有沒有原始碼的修改權限。第一條路是 @Tool 註解——你自己專案裡的業務方法，直接在方法上標註，最簡單，我們這章主要用它。第二條路是 ToolCallback，適合掛接外部或唯讀的工具：如果是第三方 JAR、你沒辦法加註解，就用 MethodToolCallback 以反射包裝現有方法；如果需要客製化邏輯，就用 FunctionToolCallback，拿 Lambda 加 DTO 封裝。但不管走哪一條，有一條安全紅線不能踩：工具一律透過既有的 Service 層拿資料，絕對不要讓模型直接碰資料庫連線、或繞過你的商業規則。Service 層有交易、有驗證、有權限，AI 只是多了一個呼叫入口，安全責任邊界不能因為接了 AI 就破洞。這個架構還有個好處：模型看到的永遠是統一的工具介面，背後是資料庫、內部 Service 還是第三方 API，隨時可以替換擴充，模型的呼叫方式完全不用改。

我們現在來動手。把講義裡的提示詞複製給 AI Agent：建立 CustomerTools，用 @Tool 包裝既有的 CustomerService，提供 getCustomers 關鍵字查詢跟 getCustomerDetail 查等級、產業、聯絡方式；再建立 OpportunityTools 包裝 OpportunityService，提供 getOpportunities 查某客戶所有銷售機會、getDealValue 查金額與成交機率；最後在 ChatController 的呼叫鏈用 .tools() 把兩個工具類別掛上去。這裡有個細節特別重要：每個 @Tool 的 description 要用中文清楚描述「什麼情況下該呼叫這個工具」——記住，這段文字不是註解，是寫給大模型看的說明書，它寫得好不好，直接決定模型會不會在對的時機挑對工具。

做完之後我們來驗證。問它一句：「台積電目前的客戶等級是什麼？有哪些進行中的銷售機會？」你會看到兩件事：第一，後端日誌裡出現工具被呼叫的紀錄，證明 AI 真的去查了；第二，回答裡的等級、商機名稱、金額，跟你資料庫裡的一模一樣。再試一個資料庫裡不存在的客戶，AI 會告訴你查無此客戶，而不是編一段故事。這一刻，你的助理就從聊天玩具升級成能引用真實客戶資料的企業助手了。

總結一句：Tool Calling 讓 AI 成為業務邏輯的呼叫者，數字由工具算、文字由模型寫、查無資料不亂答。下一節我們處理體驗面——用 SSE 把回覆一個字一個字串流到 React 前端，做出打字機效果。

# 章節 6 作業 1｜完成 AI 對話功能

## 單元定位

本作業要驗收的能力：在自己的 CRM 專案上完成本章全部實作——ChatClient 對話入口、對話記憶與 Session 隔離、Tool Calling 查詢真實資料、SSE 前端串流與認證整合。這是全課信任邊界的驗收點：AI 回答必須能引用真實客戶資料。

與前後章的銜接：完成本作業後，你的 CRM 就是一套「會讀企業真實數據」的 AI 應用；第七章將在此基礎上加入 RAG、pgvector 與 MCP 知識庫擴充。

## 作業說明

依序完成以下實作任務（對應 u6-t1 ～ u6-t9）：

1. **u6-t1**：確認模型端點與金鑰配置（Groq base-url 覆寫、`GROQ_API_KEY` 環境變數，金鑰不寫死在程式碼中）。
2. **u6-t2**：完成 ChatClient 串流流程閱讀（理解輸入 → Advisor → Tools → 模型回應的呼叫鏈）。
3. **u6-t3**：整合 Spring Security，透過 Principal 隔離對話 Session。
4. **u6-t4**：辨識專案中可抽成工具的方法（既有 Service 層的查詢方法）。
5. **u6-t5**：整理 `@Tool` 與 `ToolCallback` 差異（含 `MethodToolCallback`、`FunctionToolCallback` 的適用場景）。
6. **u6-t6**：記錄 1 個 AI 查客戶即時資料情境（提問、被呼叫的工具、回答與資料庫的比對結果）。
7. **u6-t7**：理解 SSE（Server-Sent Events）單向串流原理與安全限制（EventSource 無法自訂 Header）。
8. **u6-t8**：升級後端 `JwtAuthenticationFilter` 支援網址 Query Token。
9. **u6-t9**：使用 React 實作 EventSource 帶 Token 監聽與狀態更新（token-by-token 打字機效果、清除對話時重建 Session）。

**驗收標準**（對應本章驗證提示詞）：

- 問一個重點客戶（例如亞太智能製造）的等級和進行中生意，AI 回答的金額、次數要跟資料庫一致。
- 不同使用者（不同登入身分）的對話記憶各自獨立、不互相污染。
- 前端聊天室有逐字串流效果，且只有已登入的使用者能建立串流連線。
- 問一個資料庫中不存在的客戶，AI 應回覆查無資料，而不是編造答案。

## 口語稿

這一章的作業，就是把我們四個單元講的東西，在你自己的 CRM 專案上完整跑一遍：完成 AI 對話功能。我把要求跟驗收標準交代清楚，你照著做，做完就知道自己有沒有真的掌握。

作業一共九個任務，其實就是三組。第一組是對話基礎，任務一到三：先確認模型端點跟金鑰配置——Groq 的 base-url 有覆寫、API Key 用環境變數讀，我再囉嗦一次，金鑰寫死在程式碼裡的，這項直接不合格；然後把 ChatClient 的串流流程完整讀一遍，你要能講出一句話進來之後，經過哪些 Advisor、什麼時候碰到工具、回應怎麼流出去；最後整合 Spring Security，用 Principal 來隔離對話 Session——不是隨便傳個 sessionId 參數就好，而是用登入者的身分當隔離依據，這樣別人想冒用都沒有空間。

第二組是工具呼叫，任務四到六。先在你的專案裡辨識哪些方法可以抽成工具——原則上就是既有 Service 層的查詢方法；接著整理一份 @Tool 跟 ToolCallback 的差異筆記，包含 MethodToolCallback 跟 FunctionToolCallback 各自什麼時候用，這份筆記是要你自己講得出選型理由，不是抄講義；然後記錄一個 AI 查客戶即時資料的完整情境：你問了什麼、後端日誌顯示哪個工具被呼叫、AI 回答的數字跟資料庫比對的結果。這個紀錄很重要，它就是「數字由工具算、文字由模型寫」的證據。

第三組是前端串流，任務七到九。先理解 SSE 單向串流的原理跟它的安全限制——你要能說出為什麼 AI 聊天選 SSE 不選 WebSockets，以及 EventSource 不能自訂 Header 這個坑；然後升級後端的 JwtAuthenticationFilter，讓它支援從網址 Query 參數收 Token；最後用 React 實作 EventSource 帶 Token 的監聽與狀態更新，做出一個字一個字跳出來的效果，而且清除對話時記得連 Session 一起重建。

驗收標準有四條，缺一不可。第一條，問一個重點客戶、比如亞太智能製造，它的等級跟進行中的生意，AI 回答的金額、次數必須跟資料庫一致——你自己先去資料庫查一次，再問 AI 比對，一個數字都不能差。第二條，開兩個不同帳號登入，各聊各的，兩邊的記憶必須完全獨立、不能串味。第三條，前端要有逐字串流效果，而且沒登入的人連不上串流介面——你可以登出之後直接打那個網址試試，要被擋下來才對。第四條，也是我最在意的一條：問一個資料庫裡根本不存在的客戶，AI 必須老實說查無資料，不能編故事。查無資料不亂答，這是整門課的信任底線，過不了這條，前面做得再漂亮都不算數。

交作業的時候，把這四條驗證的過程截圖或錄影下來，加上你的工具選型筆記跟那份查資料情境紀錄。做完這份作業，你的 CRM 就正式從「一套資訊系統」變成「一套會讀企業真實數據的 AI 應用」了。下一章，我們要再往上疊一層：用 RAG 跟 pgvector 讓 AI 不只會查資料庫，還會讀公司的知識文件。我們第七章見。

# 01-ai-chat-and-memory｜AI 對話與記憶旁白稿

本稿依據 `01-ai-chat-and-memory.md` 的教學素材與口語稿整理，供人工錄音使用。共 8 段，錄音時可依段落分開保存，方便後續與投影片時間軸對齊。

建議錄音格式：WAV 或 MP3。每段開頭保持自然，結尾保留約 0.5 秒空白。

## 01｜分水嶺：聊天玩具與企業助理

建議檔名：`01-watershed.wav`

歡迎來到第六章，這一章可以說是整門課的分水嶺。上一章我們把 React 前端工作台做完了，現在你手上是一套可以登入、可以查客戶的完整 CRM。接下來，我們要讓它長出 AI 的能力。

先問你一個問題：寫一支程式去呼叫 ChatGPT 的 API，把回答印出來，這樣算不算 AI 應用？老實說，那只是一個聊天玩具。你問它「亞太智能製造這個客戶最近的生意機會金額是多少」，它會一本正經地編一個數字給你，因為它根本看不到你資料庫裡的東西。

## 02｜本章核心口訣

建議檔名：`02-core-motto.wav`

企業要的不是會聊天的玩具，而是能讀企業真實數據、講的每個數字都有憑有據的助理。所以這一章的核心口訣，我會反覆講到你耳朵長繭：「數字由工具算、文字由模型寫，查無資料不亂答」。這條信任邊界，就是聊天玩具跟企業級 AI 應用的分界線。

回顧一下我們走到哪裡了：後端有 REST API、資料落在 PostgreSQL、有 JWT 權限控管，前端有 React 工作台。這一節的任務，就是把 AI 真正接進這套系統的第一步——建立對話入口，讓 AI 會說話、會記得上下文。

## 03｜ChatClient：客服總機

建議檔名：`03-chatclient.wav`

那要從哪裡接？Spring AI 2.0 給我們的高階入口叫 ChatClient。你可以把它想像成一個客服總機：總機自己不處理所有問題，但它知道使用者的話該送去哪裡、要不要帶上之前的對話記憶、要不要叫工具幫忙查資料。所有東西都掛在這條呼叫鏈上。

建 ChatClient 的時候有幾個設定你要認得：defaultSystem 是系統提示詞，定義 AI 的角色——我們這裡就是「你是一個親切的 CRM 智慧助手」，之後信任邊界的規矩也是寫在這裡；defaultOptions 設定模型跟溫度；defaultAdvisors 掛攔截增強器，最重要的就是 MessageChatMemoryAdvisor——它會自動把某個 sessionId 的歷史對話撈出來塞進上下文，回答完再自動存回去。記憶，就是這樣來的。

## 04｜模型端點與金鑰

建議檔名：`04-groq-api-key.wav`

模型從哪裡來？我們用 Groq。因為它提供跟 OpenAI 相容的 API，所以不用換依賴，直接用 Spring AI 的 OpenAI Starter，只要在 application.yml 把 chat 的 base-url 覆寫成 Groq 的端點就好。你先到 console.groq.com 建一個免費的 API Key，用環境變數 GROQ_API_KEY 設定進去——網址跟設定範例都在教學網站上，不用抄。

這裡有一條工程紀律：金鑰一定放設定檔、用環境變數讀取，絕對不要寫死在程式碼裡，不然哪天推上 GitHub 就是資安事故。順帶一提，第七章要用的 Embedding 我們走 Voyage AI，每個月有五千萬 tokens 的免費額度，一樣是 OpenAI 相容介面，直接設定在 embedding 區塊就好。

## 05｜記憶設計的三條鐵律

建議檔名：`05-memory-rules.wav`

再來是記憶的設計，這裡有三條鐵律。第一，不同使用者要對應不同 sessionId——想像業務 A 在跟 AI 討論客戶的報價策略，業務 B 一問話竟然看得到 A 的上下文，這在企業裡是災難。第二，記憶絕對不能全站共用，不然上下文會互相污染，AI 會把不同人的對話攪在一起亂答。第三，使用者按「清除對話」的時候，session 識別值要一併重建，不是只把畫面清空。

而且我們後面會更進一步，直接整合 Spring Security，用登入者的 Principal 當隔離依據，這樣連 sessionId 被亂傳的空間都沒有。

## 06｜交給 AI Agent 動手做

建議檔名：`06-hands-on.wav`

我們現在來實際做一次。提示詞不用抄，教學網站跟講義裡都有完整原文，直接複製給你的 AI Agent：在現有 CRM 專案加入 AI 對話功能、設定 Groq 的 base-url、模型用 openai/gpt-oss-120b、系統提示詞是親切的 CRM 智慧助手、用 SSE 串流回覆並掛上記憶、以 sessionId 隔離對話。

你在課堂上要做的，不是記這段提示詞怎麼打，而是理解它為什麼這樣寫：需求講清楚、金鑰放設定、記憶要隔離。這幾件事講明白了，AI 才會照正確的架構幫你把程式生出來。

## 07｜驗收：記憶有掛上、而且是隔離的

建議檔名：`07-verify-memory.wav`

跑完之後你會看到專案多了一個對話 endpoint。啟動起來測試：先自我介紹「我叫凱文」，再問「我剛剛說我叫什麼？」——你會看到 AI 記得你的名字。然後換一個 sessionId 再問一次，它就不認識你了。

這兩個結果合在一起，才算驗收通過：記憶有掛上，而且是隔離的。少了任何一半，都代表 Advisor 或 sessionId 的設定有問題。

## 08｜本節總結與下一節

建議檔名：`08-closing.wav`

總結一下：這一節我們用 ChatClient 建好了對話總機，掛上了以 sessionId 隔離的記憶。但現在的它還是個「只會講話」的助理，你問它客戶資料它還是會瞎編。

下一節，我們就用 Tool Calling 讓它把手伸進真實的資料庫——記住口訣，數字由工具算、文字由模型寫。我們下一節見。

## 邊念邊操作提示卡

1. 先顯示非敏感的 provider/model 設定，念到 API key 時只展示環境變數名稱，不要讓秘密進畫面或 log。
2. 執行第一句對話，停在 response；再用同一 session 追問，展示記憶如何被帶入；換 session 重問，讓學員看見隔離。
3. 執行清除記憶，確認下一句不再知道前文；若模型錯誤，保留 status 和第一個錯誤。
4. 結尾保存 prompt、兩個 session 和設定證據，說明下一節會加入工具。

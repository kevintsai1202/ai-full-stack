# 章節 9 單元 1｜superpowers 功能介紹

## 單元定位

本節要解決的問題：前八章我們手動走完了一套系統的完整開發流程，建立了判斷 AI 產出對錯的 Domain Knowhow；但當你要開一個「全新專案」時，怎麼讓 AI 不是想到哪寫到哪，而是有紀律地走完「先想清楚 → 照計畫做 → 驗證才算完成」？本節介紹 Claude Code 的 superpowers 技能組——把全課貫穿的「先讀需求 → 產程式 → 驗證」三原則，制度化成一組可以自動觸發的工作流。

與前後節的銜接：本節是講師加碼章（章節 9）的第一節，承接章節 8 的結訓專案；下一節（單元 2）介紹負責「品味」的 ui-ux-pro-max，第三節介紹負責「記憶」的 deep-memory。

建議時長：15～20 分鐘（概念介紹，不含實作）。

## 教學素材

### 為什麼需要 superpowers：從手動紀律到制度化紀律

前面 8 個章節帶你手動走過開發一套系統的完整流程——這是為了讓你建立 Domain Knowhow，能判斷 AI 產出的對錯。實際開發時，我們改用 Claude Code 的 superpowers 技能組：先把需求與規格想清楚、寫成計畫，再讓 AI 照計畫實作與驗證，而不是想到哪寫到哪。

superpowers 的各技能可以分成四大階段：

### 階段一：規劃——先想清楚再動手

- **brainstorming（需求發想）**：在寫任何程式前，先釐清「要做什麼、為誰做、有哪些取捨與邊界」，把模糊的想法收斂成明確需求。
- **writing-plans（撰寫實作計畫）**：把需求轉成一份可執行的多步驟計畫：拆解任務、定義每一步的產出與驗收標準，作為開發藍圖。

### 階段二：執行——照計畫穩定產出

- **executing-plans（執行計畫）**：依計畫逐步實作，每完成一個段落就停下來檢查，確保不偏離藍圖。
- **subagent-driven-development（子代理開發）**：把計畫中彼此獨立的任務分派給子代理並行完成，加速開發。
- **test-driven-development（測試驅動開發）**：先寫測試再寫實作，用測試守住正確性，避免「看起來會動但其實錯」。
- **using-git-worktrees（Git Worktree 隔離）**：為新功能建立獨立的工作目錄，與主工作區隔離，避免互相干擾。

### 階段三：品質——除錯與審查

- **systematic-debugging（系統化除錯）**：遇到 bug 時先建立假設、逐一驗證找出根因，而不是亂試一通。
- **requesting-code-review（請求程式碼審查）**：完成一個段落後，主動請另一個代理以審查者角度檢視程式碼品質與風險。
- **receiving-code-review（回應審查意見）**：有條理地處理審查回饋，逐項修正或說明。
- **verification-before-completion（完工前驗證）**：宣告「做完」之前，實際執行並觀察行為，確認真的做對、做完。

### 階段四：收尾與進階

- **finishing-a-development-branch（收尾開發分支）**：功能完成、測試通過後，協助決定如何整合：合併、開 PR 或清理分支。
- **dispatching-parallel-agents（派發並行代理）**：面對多個彼此獨立、無先後相依的任務時，同時派發多個代理處理。
- **using-superpowers（技能入口）**：所有任務的起點：判斷該用哪個技能，並確保照技能流程確實執行。

### 在 AI CRM 專案中的對應

回頭看我們這門課做過的事，你會發現 superpowers 每一個技能都對得上：章節 1 講的「先讀需求再產程式」對應 brainstorming；章節 2 的 CRM Domain Modeling 對應 writing-plans；章節 8 的測試策略對應 test-driven-development 與 verification-before-completion；我們每章排錯時堅持「貼實際訊息、找根因」，就是 systematic-debugging。差別在於：課堂上這些紀律靠你自己維持，用了 superpowers 之後，這些紀律由技能流程強制執行——AI 想跳過驗證直接說「做完了」，流程本身不允許。

## 口語稿

嗨，歡迎來到第九章。恭喜你，走到這裡，你的 AI CRM 已經能登入、能查客戶、會給銷售建議，還能追蹤 AI 的決策過程——這是一個真的可以放進履歷的作品。這一章是我的加碼章，我想跟你聊三個技能，它們回答同一個問題：當你離開這門課、要開一個全新專案的時候，怎麼讓 AI 協作有紀律、有品味、有記憶？這一節我們先講紀律。

先說一個你可能已經有感覺的現象。前八章我們跟 AI 協作的時候，我一直在旁邊碎碎念三件事：先讀需求、再產程式、最後一定要驗證。為什麼我要一直念？因為 AI 的天性就是「你講一句它就衝」。你說「幫我加一個客戶標籤功能」，它馬上開始寫程式——需求還沒釐清、資料模型還沒想、測試更是想都沒想。小功能可能沒事，但專案一大，這種「想到哪寫到哪」的做法一定出事。前八章我們靠人工把關，那有沒有辦法把這個把關制度化？有，這就是 superpowers。

superpowers 是 Claude Code 上的一組技能，你可以把它想成「一套強制的開發 SOP」。它把我們整門課的三原則，拆成了十幾個具體的技能，我用四個階段帶你看一遍。

第一個階段是規劃。裡面有兩個技能：brainstorming 跟 writing-plans。brainstorming 就是需求發想——在寫任何程式之前，先把「要做什麼、為誰做、有哪些取捨跟邊界」想清楚，把模糊的想法收斂成明確需求。你還記得第一章我們挑 CRM 當題目的時候，花了多少時間討論「業務到底要什麼」嗎？那就是 brainstorming 在做的事。想清楚之後，writing-plans 把需求變成一份可執行的計畫：任務怎麼拆、每一步的產出是什麼、驗收標準是什麼。這份計畫就是開發藍圖，之後所有的實作都要對著它走。

第二個階段是執行。executing-plans 讓 AI 照著計畫一步一步做，每完成一個段落就停下來檢查，不偏離藍圖。test-driven-development 是測試驅動開發，先寫測試再寫實作——這個特別重要，因為 AI 最會的就是寫出「看起來會動但其實錯」的程式，測試先行就是把驗收標準寫在程式前面，讓它沒辦法蒙混過關。另外還有 using-git-worktrees，幫每個新功能開一個獨立的工作目錄，跟主工作區隔離；以及 subagent-driven-development，把計畫裡彼此獨立的任務分給多個子代理同時做，速度會快很多。

第三個階段是品質。systematic-debugging 是系統化除錯——遇到 bug 先建立假設、逐一驗證找根因，而不是亂試一通。這跟我們每一章排錯時講的「把錯誤訊息原封不動貼給 AI、找出根本原因」是同一件事。再來是一對很有趣的技能：requesting-code-review 跟 receiving-code-review。寫完一個段落，讓另一個 AI 代理用審查者的角度來挑毛病，然後有條理地逐項回應。你沒看錯，是 AI 審 AI——因為寫程式的那個代理會有盲點，換一雙眼睛看，很多問題會浮出來。最後是我認為最關鍵的 verification-before-completion：在宣告「做完」之前，必須實際執行、觀察行為，確認真的做對做完。這就是我們三原則的最後一條，只是現在它變成流程的一部分，AI 想跳過都跳不過。

第四個階段是收尾。finishing-a-development-branch 幫你決定功能完成後怎麼整合——合併、開 PR、還是清理分支。而整組技能的入口叫 using-superpowers，它是所有任務的起點，負責判斷這個任務該走哪個技能、並且確保流程被確實執行。

那什麼時機用？我的建議是：只要是「會改變系統行為的開發」，就讓它走完整流程——新功能走 brainstorming 加 TDD，修 bug 走 systematic-debugging。如果只是查資料、改個錯字，當然不必大陣仗。重點是那個判斷要在動手前做，不是做到一半才想起來。

總結一下：superpowers 不是什麼新魔法，它就是把我們整門課「先讀需求、產程式、驗證」的紀律制度化，讓紀律不再靠你的意志力，而是靠流程。下一節，我們來看另一個問題：AI 寫的介面為什麼常常「能用但很醜」？我們用 ui-ux-pro-max 給 AI 補上品味。下一節見。

# 01-superpowers｜superpowers 功能介紹旁白稿

本稿依據 `01-superpowers.md` 的教學素材與口語稿整理，供人工錄音使用。共 9 段，錄音時可依段落分開保存，方便後續與投影片時間軸對齊。

建議錄音格式：WAV 或 MP3。每段開頭保持自然，結尾保留約 0.5 秒空白。

## 01｜第九章開場：紀律、品味、記憶

建議檔名：`01-chapter-intro.wav`

嗨，歡迎來到第九章。恭喜你，走到這裡，你的 AI CRM 已經能登入、能查客戶、會給銷售建議——這是一個真的可以放進履歷的作品。這一章是我的加碼章，屬於進階加值內容，我想跟你聊三個 Claude Code 的技能，它們回答同一個問題：當你離開這門課、要開一個全新專案的時候，怎麼讓 AI 協作有紀律、有品味、有記憶？這一節我們先講紀律。

## 02｜AI 的天性：你講一句它就衝

建議檔名：`02-ai-nature.wav`

先說一個你可能已經有感覺的現象。前八章我們跟 AI 協作的時候，我一直在旁邊碎碎念三件事：先讀需求、再產程式、最後一定要驗證。為什麼要一直念？因為 AI 的天性就是「你講一句它就衝」。你說「幫我加一個客戶標籤功能」，它馬上開始寫程式——需求還沒釐清、資料模型還沒想、測試更是想都沒想。小功能可能沒事，但專案一大，這種「想到哪寫到哪」的做法一定出事。前八章我們靠人工把關，那有沒有辦法把這個把關制度化？有，這就是 superpowers。

## 03｜superpowers 是一套強制的開發 SOP

建議檔名：`03-what-is-superpowers.wav`

superpowers 是 Claude Code 上的一組技能，你可以把它想成「一套強制的開發 SOP」。它把我們整門課的三原則，拆成了十幾個具體的技能。這一節是概念介紹，你不用背任何技能名稱，名稱跟細節教學網站都查得到，你只要理解四個階段各自在守什麼。

## 04｜階段一：規劃——先想清楚再動手

建議檔名：`04-stage-planning.wav`

第一個階段是規劃，裡面有兩個技能。brainstorming 是需求發想——在寫任何程式之前，先把「要做什麼、為誰做、有哪些取捨跟邊界」想清楚，把模糊的想法收斂成明確需求。還記得第一章我們挑 CRM 當題目時，花了多少時間討論「業務到底要什麼」嗎？那就是 brainstorming 在做的事。想清楚之後，writing-plans 把需求變成一份可執行的計畫：任務怎麼拆、每一步的產出跟驗收標準是什麼。這份計畫就是開發藍圖，之後所有實作都要對著它走。

## 05｜階段二：執行——照計畫穩定產出

建議檔名：`05-stage-execution.wav`

第二個階段是執行。executing-plans 讓 AI 照著計畫一步一步做，每完成一個段落就停下來檢查，不偏離藍圖。test-driven-development 是測試驅動開發，先寫測試再寫實作——這個特別重要，因為 AI 最會的就是寫出「看起來會動但其實錯」的程式，測試先行就是把驗收標準寫在程式前面，讓它沒辦法蒙混過關。另外還有 using-git-worktrees，幫每個新功能開一個獨立的工作目錄；以及 subagent-driven-development，把彼此獨立的任務分給多個子代理同時做，速度會快很多。

## 06｜階段三：品質——除錯與審查

建議檔名：`06-stage-quality.wav`

第三個階段是品質。systematic-debugging 是系統化除錯——遇到 bug 先建立假設、逐一驗證找根因，而不是亂試一通，這跟我們每一章排錯時講的「把錯誤訊息原封不動貼給 AI」是同一件事。再來是一對很有趣的技能：requesting-code-review 跟 receiving-code-review——讓另一個 AI 代理用審查者的角度來挑毛病，再有條理地逐項回應。你沒看錯，是 AI 審 AI，因為寫程式的那個代理會有盲點。最後是我認為最關鍵的 verification-before-completion：宣告「做完」之前，必須實際執行、觀察行為。這就是三原則的最後一條，只是現在它變成流程的一部分，AI 想跳過都跳不過。

## 07｜階段四：收尾與技能入口

建議檔名：`07-stage-finishing.wav`

第四個階段是收尾。finishing-a-development-branch 幫你決定功能完成後怎麼整合——合併、開 PR、還是清理分支。而整組技能的入口叫 using-superpowers，它是所有任務的起點，負責判斷這個任務該走哪個技能，並且確保流程被確實執行。

## 08｜什麼時機用

建議檔名：`08-when-to-use.wav`

那什麼時機用？我的建議是：只要是「會改變系統行為的開發」，就讓它走完整流程——新功能走 brainstorming 加 TDD，修 bug 走 systematic-debugging。如果只是查資料、改個錯字，當然不必大陣仗。重點是那個判斷要在動手前做，不是做到一半才想起來。

## 09｜總結與下一節

建議檔名：`09-closing.wav`

總結一下：superpowers 不是什麼新魔法，它就是把我們整門課「先讀需求、產程式、驗證」的紀律制度化，讓紀律不再靠你的意志力，而是靠流程。下一節，我們來看另一個問題：AI 寫的介面為什麼常常「能用但很醜」？我們用 ui-ux-pro-max 給 AI 補上品味。下一節見。

## 邊念邊操作提示卡

1. 開場先打開 AGENTS、需求文件和 `git status`，旁白念到「先確認範圍」時停下來，不要直接進程式碼。
2. 依需求、設計、測試、最小實作、驗證、review 的順序切畫面；每一步保留檔案或命令證據。
3. 示範 AI 產生小 patch 後閱讀 diff，再執行測試；若失敗，保留第一個錯誤和 unresolved 狀態。
4. 最後執行 `git diff --check` 和針對性測試，展示 checklist 和實際輸出。

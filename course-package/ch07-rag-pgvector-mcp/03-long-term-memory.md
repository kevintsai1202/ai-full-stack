# 章節 7 單元 3｜長期記憶與企業共同知識

## 單元定位

單元 1 的知識庫解決了「AI 讀公司文件」的問題，但 AI 對「你跟它聊過什麼」依然健忘——ChatMemory 只能記最近幾輪，一開新對話就全部歸零。本節把 RAG 的技術複用到對話歷史上：把每一次問答與 AI 給過的建議向量化存進 pgvector，讓助手擁有跨對話、跨數週甚至數月的長期記憶，並累積成企業的共同知識。三個關鍵設計：非同步寫入不拖慢串流回覆、Metadata 隔離不同使用者的記憶、雙路檢索同時查文件與歷史再合併。建議時長：20～25 分鐘。

## 教學素材

### 為什麼需要對話歷史 RAG

基本的 ChatMemory（對話記憶）只能儲存最近幾次對話（短期記憶），且受限於大模型上下文窗口（Context Window）的長度與 Token 開銷。當用戶問到「幾天前我們討論過的那個方案」時，短期記憶無能為力。

藉由將「歷史問答」向量化寫入資料庫，我們可以使用 RAG 搜尋「語意相似的過去對話」，動態將相關記憶塞入 Prompt，使 AI 具備橫跨數週甚至數月的長期語意記憶。

- 短期記憶（ChatMemory）：儲存於記憶體，限制 N 筆對話，成本高且會隨重啟消失
- 長期記憶（History RAG）：向量化存入 PostgreSQL（pgvector），需要時以語意搜尋檢索，開銷小且永久保存

### 三個關鍵設計

**1. 非同步寫入，避免拖慢回覆**

在 SSE 串流介面用 `doOnNext` 收集完整回覆內容，並在 `doOnComplete` 時以 `CompletableFuture.runAsync` 非同步寫入向量庫，避免阻塞串流回應——使用者感受不到任何延遲，記憶卻在背景默默累積。

**2. Metadata 隔離與精確過濾**

每份寫入的記憶 Document 在 metadata 標上 `sessionId`、`type`（如 `chat_history`）與建立時間。查詢時用 filterExpression 過濾，確保 A 使用者的記憶不會漏給 B 使用者，也能把「文件知識」與「對話記憶」分流。

**3. 雙路 RAG 檢索與上下文合併**

使用者提問時同時查兩路：客戶文件（`type` 為 `customer_doc`）取前 3 筆、該使用者的歷史對話（`type` 為 `chat_history` 且 `sessionId` 相符）取前 2 筆，合併後作為上下文交給模型——AI 同時擁有「公司知識」與「你的脈絡」。

### 從個人記憶到企業共同知識

把 AI 給過的每一次評估與建議也收進知識庫，不只是個人方便：歷史對話與 AI 建議沉澱成可被搜尋的資產後，整個團隊都能受益，AI 越用越懂你的客戶，這就是企業共同知識的雛形。

## 示範與提示詞

**AI Agent 提示詞 — 對話歷史長期記憶**

```text
請為聊天室加入「長期記憶」功能，把對話歷史向量化存入 pgvector：
1. 建立 ChatHistoryService，提供 saveToVectorStore(sessionId, prompt, response) 方法：把使用者問句與 AI 回答組成一份 Document，metadata 加上 sessionId、type 為 chat_history 與建立時間，再寫入 VectorStore。
2. 修改 SSE 串流介面：用 doOnNext 收集完整回覆內容，並在 doOnComplete 時用 CompletableFuture.runAsync 非同步寫入向量庫，避免阻塞串流回應。
3. 實作雙路 RAG 檢索方法：使用者提問時同時查兩路 —— 客戶文件（filterExpression 過濾 type 為 customer_doc）取前 3 筆、該使用者的歷史對話（type 為 chat_history 且 sessionId 相符）取前 2 筆，合併後作為上下文交給模型。
4. 程式碼需有中文函式註解。
完成後請示範驗證流程：先聊「我專注半導體產業客戶、偏好 VIP 等級」，之後開新對話問「根據我之前說的需求推薦適合的客戶」，確認 AI 記得歷史偏好。
```

**口語化任務提示詞 — 讓 AI 把歷史對話和建議也記進知識庫［build］**

```text
請幫 AI 助手加上「長期記憶」：把每一次的對話內容、還有 AI 給過的建議，也一併收進可被搜尋的知識庫裡。這樣下次我再問問題時，AI 會自動翻出相關的歷史對話和過去給過的建議當作參考，就算是開一段全新的對話，也記得我先前說過的偏好和客戶的脈絡。（存這些記憶時請用不會拖慢回覆速度的方式。）請加中文註解。
```

## 口語稿

上一節我們聊了 MCP 和 Skills，這一節回到 RAG，但換一個對象——這次要向量化的不是公司文件，而是「你跟 AI 的對話」。先講為什麼。你有沒有遇過這種情況：你昨天跟 AI 助理聊了半小時，交代了你專注半導體產業的客戶、偏好 VIP 等級，結果今天開一個新對話，它完全不記得你是誰、你說過什麼，一切從零開始。這不是它笨，是我們第六章給它的 ChatMemory 本來就只是短期記憶——它存在記憶體裡，只保留最近 N 筆對話，程式一重啟就消失，而且每一筆都要塞進上下文窗口，筆數越多 Token 開銷越大，所以不可能無限制地存。當使用者問「幾天前我們討論過的那個方案」，短期記憶是無能為力的。

那長期記憶怎麼做？答案你其實已經會了——就是 RAG。上一個單元我們把公司文件切塊、向量化、存進 pgvector，需要的時候用語意搜尋撈出來；現在把同一招用在對話歷史上：每一次的問答、AI 給過的每一個建議，都組成一份 Document 存進向量庫。下次你提問時，系統先去搜「語意相似的過去對話」，把相關的記憶動態塞進 Prompt。這樣 AI 就有了橫跨數週甚至數月的長期語意記憶，而且成本很低——記憶存在資料庫裡永久保存，每次只撈相關的幾筆，不用把整部歷史都塞進上下文。

不過這裡有三個設計上的眉角，做錯任何一個，功能就會出問題。第一個：什麼時候寫入向量庫？注意，向量化是要呼叫 EmbeddingModel 的，有網路延遲。如果你在回覆使用者之前先做這件事，使用者就會明顯感覺變慢。所以正確做法是：在 SSE 串流的過程中用 doOnNext 一路收集完整的回覆內容，等 doOnComplete、也就是串流結束的那一刻，用 CompletableFuture.runAsync 丟到背景執行緒去非同步寫入。使用者那邊的體感完全不變，記憶卻在背景默默存好了。這就是提示詞裡那句「請用不會拖慢回覆速度的方式」背後的技術含義。

第二個眉角：記憶要隔離。想像一下業務 A 的客戶偏好被檢索出來塞進了業務 B 的對話裡，這是很嚴重的資料洩漏。解法是 Metadata：每份記憶 Document 寫入時都標上 sessionId、type 是 chat_history、還有建立時間；查詢的時候用 filterExpression 精確過濾，只撈這個使用者自己的記憶。同一招也用來把「文件知識」和「對話記憶」分流，互不干擾。

第三個眉角：檢索要走雙路。使用者問一個問題的時候，我們同時查兩路——一路查客戶文件，type 是 customer_doc，取最相關的前三筆；另一路查這位使用者自己的歷史對話，type 是 chat_history 而且 sessionId 相符，取前兩筆。兩路合併之後一起作為上下文交給模型。這樣 AI 回答的時候，手上同時有「公司的知識」和「你的脈絡」，回答才會又準又貼身。

我們現在來實際做。把提示詞交給 AI Agent，它會建立 ChatHistoryService、改造 SSE 串流介面、實作雙路檢索。完成之後的驗證流程是這一節最有感的時刻：你先開一段對話，跟它說「我專注半導體產業客戶、偏好 VIP 等級」，聊完把對話關掉；然後開一段全新的對話，問它「根據我之前說的需求，推薦適合的客戶」。你會看到，AI 真的記得你先前說過的偏好——這在以前的短期記憶架構下是不可能的。

最後我想拉高一個層次。這個功能不只是「個人助理變貼心」而已。當 AI 給過的每一次評估、每一個建議都沉澱進可被搜尋的知識庫，這些內容就從「一次性的對話」變成了「企業的共同知識資產」——AI 越用越懂你的客戶，團隊的經驗也不再隨人員流動而蒸發。總結一下：這一節我們用 RAG 打造了跨對話的長期記憶，三個關鍵是非同步寫入、Metadata 隔離、雙路檢索。下一節是本章收官——我們站在整個 CRM 的高度，來設計知識庫的內容策略：到底哪些文件值得向量化。

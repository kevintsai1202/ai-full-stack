# 03-long-term-memory｜長期記憶與企業共同知識旁白稿

本稿依據 `03-long-term-memory.md` 的教學素材與口語稿整理，供人工錄音使用。共 7 段，錄音時可依段落分開保存，方便後續與投影片時間軸對齊。

建議錄音格式：WAV 或 MP3。每段開頭保持自然，結尾保留約 0.5 秒空白。

## 01｜AI 為什麼這麼健忘

建議檔名：`01-why-ai-forgets.wav`

上一節我們聊了 MCP 和 Skills，這一節回到 RAG，但換一個對象——這次要向量化的不是公司文件，而是「你跟 AI 的對話」。

先講為什麼。你有沒有遇過這種情況：你昨天跟 AI 助理聊了半小時，交代了你專注製造業的客戶、偏好 VIP 等級，結果今天開一個新對話，它完全不記得你是誰、你說過什麼，一切從零開始。

這不是它笨，是我們第六章給它的 ChatMemory 本來就只是短期記憶——它存在記憶體裡，只保留最近 N 筆對話，程式一重啟就消失，而且每一筆都要塞進上下文窗口，筆數越多 Token 開銷越大，不可能無限制地存。當使用者問「幾天前我們討論過的那個方案」，短期記憶是無能為力的。

## 02｜長期記憶的答案：還是 RAG

建議檔名：`02-history-rag.wav`

那長期記憶怎麼做？答案你其實已經會了——就是 RAG。單元一我們把公司文件切塊、向量化、存進 pgvector，需要的時候用語意搜尋撈出來；現在把同一招用在對話歷史上：每一次的問答、AI 給過的每一個建議，都組成一份 Document 存進向量庫。

下次你提問時，系統先去搜「語意相似的過去對話」，把相關的記憶動態塞進 Prompt。這樣 AI 就有了橫跨數週甚至數月的長期語意記憶，而且成本很低——記憶存在資料庫裡永久保存，每次只撈相關的幾筆，不用把整部歷史都塞進上下文。

這就是先懂架構的好處：技術是同一套，換個對象，就多出一個全新的能力。

## 03｜眉角一：非同步寫入，不拖慢回覆

建議檔名：`03-async-write.wav`

不過這裡有三個設計上的眉角，做錯任何一個，功能就會出問題。

第一個：什麼時候寫入向量庫？注意，向量化是要呼叫 EmbeddingModel 的，有網路延遲。如果你在回覆使用者之前先做這件事，使用者就會明顯感覺變慢。

所以正確做法是：在 SSE 串流的過程中用 doOnNext 一路收集完整的回覆內容，等 doOnComplete、也就是串流結束的那一刻，用 CompletableFuture.runAsync 丟到背景執行緒去非同步寫入。使用者那邊的體感完全不變，記憶卻在背景默默存好了。這就是提示詞裡那句「請用不會拖慢回覆速度的方式」背後的技術含義。

## 04｜眉角二：Metadata 隔離記憶

建議檔名：`04-metadata-isolation.wav`

第二個眉角：記憶要隔離。想像一下業務 A 的客戶偏好被檢索出來塞進了業務 B 的對話裡，這是很嚴重的資料洩漏。

解法是 Metadata：每份記憶 Document 寫入時都標上 sessionId、type 是 chat_history、還有建立時間；查詢的時候用 filterExpression 精確過濾，只撈這個使用者自己的記憶。同一招也用來把「文件知識」和「對話記憶」分流，互不干擾。

## 05｜眉角三：雙路檢索與上下文合併

建議檔名：`05-dual-path-retrieval.wav`

第三個眉角：檢索要走雙路。使用者問一個問題的時候，我們同時查兩路——一路查客戶文件，type 是 customer_doc，取最相關的前三筆；另一路查這位使用者自己的歷史對話，type 是 chat_history 而且 sessionId 相符，取前兩筆。

兩路合併之後一起作為上下文交給模型。這樣 AI 回答的時候，手上同時有「公司的知識」和「你的脈絡」，回答才會又準又貼身。

## 06｜實作與最有感的驗證時刻

建議檔名：`06-build-and-verify.wav`

我們現在來實際做。完整提示詞在教學網站上，直接複製交給 AI Agent，它會建立 ChatHistoryService、改造 SSE 串流介面、實作雙路檢索。你在課堂上要顧的，是剛剛那三個眉角有沒有被正確做出來。

完成之後的驗證流程是這一節最有感的時刻：你先開一段對話，跟它說「我專注製造業客戶、偏好金額大的案子」，聊完把對話關掉；然後開一段全新的對話，問它「根據我之前說的需求，推薦適合的客戶」。你會看到，AI 真的記得你先前說過的偏好——這在以前的短期記憶架構下是不可能的。

## 07｜從個人記憶到企業共同知識

建議檔名：`07-closing.wav`

最後我想拉高一個層次。這個功能不只是「個人助理變貼心」而已。當 AI 給過的每一次評估、每一個建議都沉澱進可被搜尋的知識庫，這些內容就從「一次性的對話」變成了「企業的共同知識資產」——AI 越用越懂你的客戶，團隊的經驗也不再隨人員流動而蒸發。

總結一下：這一節我們用 RAG 打造了跨對話的長期記憶，三個關鍵是非同步寫入、Metadata 隔離、雙路檢索。下一節是本章收官——我們站在整個 CRM 的高度，來設計知識庫的內容策略：到底哪些文件值得向量化。我們下一節見。

## 邊念邊操作提示卡

1. 先把短期 history、session memory、企業知識三張卡放在畫面上，逐一念保存目的、owner、期限和刪除方式。
2. 從一段對話抽取 memory candidate，展示事實、來源、信心、敏感性和人工確認欄位。
3. 用同 user 查回，再換另一 user/tenant，最後刪除記憶後重查；每次停在結果讓隔離證據清楚可見。
4. 收尾指出歷史記憶不能凌駕最新 CRM 真值，保存 schema、刪除和保留期限結果。

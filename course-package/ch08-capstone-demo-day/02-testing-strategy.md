# 章節 8 單元 2｜測試策略

## 單元定位

本節要解決的問題：AI 功能的輸出有隨機性，不能用傳統「斷言輸出完全相等」的方式測試；本節建立 AI CRM 的分層測試策略、三種典型客戶場景的端到端測試，以及涵蓋安全性、效能、可觀測性與錯誤處理的上線檢查清單，讓上一節跑通的系統經得起驗收。

與前後節的銜接：本節承接單元 1 已整合完成的完整 AI CRM；也是主軸專案的最後一節。下一章（章節 9）是講師加碼的常用開發技能介紹。

建議時長：25～35 分鐘（含檢查清單逐項確認示範）。

## 教學素材

### 端到端測試案例設計：三種典型客戶場景

結訓專案需要涵蓋三種典型客戶場景，對應 Unit 3 seed data 的三種客戶類型：

1. **高價值活躍客戶（APIM）**——登入後查看客戶詳情、觸發 AI 對話、AI 能正確引用 RAG 知識庫回答產品問題。
2. **資料不足客戶**——AI 應誠實回答「查無相關資料」而非編造。
3. **流失風險客戶（GlobalMart）**——AI 摘要能正確反映互動頻率下降的趨勢。

每個場景都要**從登入開始**，走完完整的使用路徑。

### AI 功能的測試策略：分層測試

AI 功能的測試不能用傳統的「斷言輸出完全相等」方式，因為 LLM 的輸出具有隨機性。正確的策略是分層測試：

1. **Java @Tool 方法**——用一般單元測試驗證輸入輸出。
2. **Prompt 組裝**——驗證 system prompt 是否正確帶入客戶資料、是否設定了正確的角色約束。
3. **RAG 檢索**——驗證 vector store 查詢是否回傳相關文件。
4. **端到端**——用 Playwright 模擬使用者操作，驗證 SSE 串流是否正確顯示在前端。

### 上線檢查清單與效能調校

AI CRM 上線前需要檢查四大面向：

1. **安全性**——JWT secret 是否已替換為生產金鑰、CORS 白名單是否已收斂、API 是否有 rate limiting。
2. **效能**——SSE 連線是否有 timeout 設定、RAG 查詢的 topK 與 similarity threshold 是否合理、資料庫連線池大小是否足夠。
3. **可觀測性**——是否有結構化日誌、是否記錄 AI 呼叫的 token 消耗與延遲。
4. **錯誤處理**——LLM API 不可用時是否有 fallback、前端是否能優雅顯示錯誤訊息。

## 口語稿

上一節我們把 AI CRM 串起來、展示腳本也走順了，這一節我們來面對一個更根本的問題：這套系統經得起「驗」嗎？我先丟一個情境給你。假設你寫了一個傳統的測試，斷言 AI 助理回答 APIM 合約狀況時，輸出的字串要完全等於某段預期文字——這個測試今天跑是綠的，明天跑可能就紅了。為什麼？因為 LLM 的輸出天生就有隨機性，同一個問題，它每次的措辭都可能不一樣。所以 AI 功能的測試，不能用傳統「斷言輸出完全相等」的方式，硬套只會做出一堆時好時壞的假測試。那怎麼辦？答案是分層測試——把 AI 功能拆開來，每一層用適合它的方式驗。

我們一層一層看。第一層是 Java 的 @Tool 方法，這一層根本沒有隨機性，就是普通的 Java 程式，用一般的單元測試驗證輸入輸出就好——給它客戶 ID，它回傳的合約資料對不對，斷言下去就是了。第二層是 Prompt 組裝：驗證 system prompt 有沒有正確帶入客戶資料、有沒有設定正確的角色約束——這測的是「我們餵給模型的東西對不對」，同樣是確定性的。第三層是 RAG 檢索：驗證 vector store 查詢有沒有回傳相關文件——問退貨政策，撈回來的該是退貨政策的文件，而不是產品規格書。第四層才是端到端：用 Playwright 模擬真實使用者操作，驗證 SSE 串流有沒有正確顯示在前端。你發現了嗎？四層裡面有三層其實都是確定性的測試，真正碰到模型隨機性的只有最後一層，而那一層我們驗的是「流程有沒有走通、格式對不對」，不是逐字比對。這就呼應我們整門課的信任邊界口訣：數字由程式算、文字由 AI 寫——能用程式驗的部分，就用程式紮紮實實地驗。

那端到端要測哪些場景？我們挑三種典型客戶，剛好對應第三章 seed data 埋好的三種客戶類型。第一種，高價值活躍客戶 APIM：登入後查看客戶詳情、觸發 AI 對話，AI 要能正確引用 RAG 知識庫回答產品問題——這是「資料齊全時答得好」。第二種，資料還很少的客戶：AI 應該誠實回答「查無相關資料」，而不是編造——這是「資料不足時不亂答」，也是第六章那條信任邊界守則的最終考驗。第三種，流失風險客戶 GlobalMart：AI 摘要要能正確反映互動頻率下降的趨勢——這是「AI 洞察反映真實資料」。注意一個細節：三個場景都要從登入開始走完完整的使用路徑，因為 Demo Day 跟真實使用者都是從登入開始的，只測中間一小段是不夠的。

測試齊了，最後一關是上線檢查清單。我們現在來實際跑一次，我貼上教材裡的提示詞：「請幫我整理一份上線前的檢查清單，並逐項幫我檢查。」你會看到 AI 列出四大面向，我們一項一項看。第一是安全性：JWT secret 換成生產金鑰了嗎？開發時圖方便寫死的那把 key 絕對不能上線；CORS 白名單收斂了嗎？API 有 rate limiting 嗎？第二是效能：SSE 連線有沒有 timeout 設定、RAG 查詢的 topK 跟 similarity threshold 合不合理、資料庫連線池大小夠不夠。第三是可觀測性：有沒有結構化日誌？有沒有記錄每次 AI 呼叫的 token 消耗跟延遲？AI 功能是要花錢的，token 花在哪裡你得看得見。第四是錯誤處理：LLM API 掛掉的時候有沒有 fallback？前端能不能優雅地顯示錯誤訊息，而不是白畫面？這四個面向逐項打勾，再配上同一段提示詞幫你準備的一條龍展示腳本——登入、看客戶清單、跟 AI 對話、看客戶評估與風險、看儀表板分析圖表、看團隊分析、最後用知識庫做一次文件問答——你的結訓驗收就完整了。

好，走到這裡，主軸專案正式收官。回頭看看，從第一章的一台空機器開始：裝環境、寫 API、資料落地、加上安全防護、蓋出前端工作台、接上 AI 對話、建好 RAG 知識庫，到今天完成整合、測試與上線檢查——你帶走的不是一份聽課筆記，而是一套有登入、有資料、有 AI 助理、有知識庫、有測試、有上線清單的完整企業級作品。把它放進履歷、放上 GitHub，面試時照著上一節的腳本展示一遍，這就是你這門課最實在的成果。那課程還沒完全結束——下一章是我加碼的「常用開發技能介紹」，我會分享幾套讓 AI 協作開發更有紀律、更能累積的 Agent 技能，包括規格驅動開發的 superpowers、UI/UX 設計智能的 ui-ux-pro-max，還有記憶類技能 deep-memory。恭喜你完成結訓專案，我們下一章見。

# 章節 8 單元 1｜完整 AI CRM 功能示範

## 單元定位

本節要解決的問題：把前七章各自完成的產出——登入認證、客戶管理、AI 對話、風險與情緒洞察、團隊分析、RAG 知識查詢——真正「串起來」，變成一套可以從頭到尾展示的 AI CRM 系統，並排除整合階段最常見的 CORS、JWT 串接與 Seed Data 對齊問題。

與前後節的銜接：本節承接章節 7 完成的 RAG 知識庫功能，是全課的整合收官節；下一節（單元 2）會在跑通的系統上建立端到端測試策略與上線檢查清單。

建議時長：25～35 分鐘（含完整 Demo 流程實際走一遍）。

## 教學素材

### 結訓專案的核心目標：不是加功能，而是串起來

結訓專案的核心目標不是新增功能，而是讓前七個單元的產出真正「串起來」成為一套可展示的產品。重點在於排除整合時的版本衝突、CORS 錯誤、環境差異，並建立可重複執行的驗證流程。

### 結訓整合的三大挑戰

把七個單元的產出串成一套可展示的系統，最常遇到三類問題：

1. **環境差異**——Docker 容器、JDK 版本、Node.js 版本在不同機器上不一致。
2. **跨層整合**——前端 Axios 的 base URL、CORS 設定、JWT token 在 header 的格式，任何一環不對就 401/403。
3. **資料流斷裂**——seed data 的客戶 ID 與前端硬編碼的測試 ID 不一致，導致查無資料。

解決方式是建立一份「整合檢查清單」，從資料庫、後端、前端**逐層驗證**，而不是看到錯誤就到處亂改。

### Demo Day 展示準備

Demo Day 的展示順序建議：

1. 先展示**登入與角色切換**，證明 Spring Security + JWT 正常運作。
2. 展示**客戶列表與商機管理**，證明 JPA + Flyway 的資料層完整。
3. 開啟 **AI 助理聊天室**，用 SSE 串流展示即時回應。
4. 提問**需要 RAG 知識的問題**（如退貨政策），展示 AI 引用正確文件回答。
5. 開啟 **Swagger UI** 展示 OpenAPI 文件。

每個步驟預先準備好測試資料，避免現場輸入導致意外。

### CRM 完整流程展示腳本

建議按以下順序展示 AI CRM 系統：

1. 登入系統（展示 JWT 認證）→ 進入 Dashboard 查看本月指標
2. 進入客戶列表 → 使用動態篩選找到 APIM → 查看客戶詳細資訊
3. 開啟 AI 助理 → 詢問「APIM 最近的合約狀況和商機進度」（展示 Tool Calling）
4. 詢問「GlobalMart 有流失風險嗎？建議怎麼處理？」（展示 RAG + 歷史記憶）
5. AI 產生行動建議 → 確認建立待辦任務（展示完整業務閉環）

## 口語稿

歡迎來到第八章，也是我們這門課的結訓章。先讓我帶你回頭看一眼我們一路走過來的路：第一章我們把環境裝好、建立了 AI 協作的三原則；第二章用 Spring MVC 做出第一批 REST API；第三章讓資料真正落地到 PostgreSQL，用 Flyway 管 Schema、用 JPA 跟動態查詢撈資料；第四章加上 Spring Security 跟 JWT，讓系統有了門禁；第五章用 React 19 蓋出 CRM 工作台；第六章接上 Spring AI，讓 AI 助理能用 SSE 串流回話、用 Tool Calling 查真實資料；第七章再用 pgvector 蓋了 RAG 知識庫，讓 AI 回答有憑有據。七章下來，你手上其實已經有一套企業級系統的所有零件了。那這一章要做什麼？我要很誠實地跟你說：這一章我們一行新功能都不寫。結訓專案的核心目標不是加功能，而是把這七個單元的產出真正「串起來」，變成一套你可以放進履歷、可以在面試時當場展示的完整作品。

聽起來很簡單對不對？零件都有了，組起來就好。但帶過專案的人都知道，整合往往是最痛的一段。整合最常遇到的問題有三類。第一類是環境差異：你的 Docker 容器、JDK 版本、Node.js 版本，在你的機器上跑得好好的，換一台機器就不一致。第二類是跨層整合：前端 Axios 的 base URL 指錯地方、CORS 設定漏了網域、JWT token 放在 header 的格式不對——這三個環節任何一環出錯，你看到的都是 401 或 403，畫面上就是一片登入失敗，而且錯誤訊息長得幾乎一模一樣。第三類是資料流斷裂：seed data 裡的客戶 ID 跟前端硬編碼的測試 ID 對不起來，系統明明活著，畫面卻永遠「查無資料」。這三類問題的共通解法只有一個：建立一份整合檢查清單，從資料庫、後端、前端逐層驗證，一層確認沒問題再往上走，千萬不要看到錯誤就前後端到處亂改，那只會把問題越攪越渾。

我們現在來實際做整合。我打開 AI 助手，貼上這段提示詞：「請接續前面所有做好的東西，把後端、網頁畫面、AI 智慧助手、客戶風險與情緒洞察、團隊分析、以及知識庫問答，全部整合成一套可以完整展示的 AI CRM，確認它們能正確一起啟動運作。」你會看到 AI 開始逐一檢查每個模組的啟動狀態，發現 CORS 或 token 格式的問題就當場修掉。注意提示詞的後半段，我還請它針對三種典型客戶建立從頭到尾的測試——這三種場景我們留到下一節細講，這一節先聚焦在「系統跑得起來、展示得出去」。

系統串起來之後，就是 Demo Day 的重頭戲：展示腳本。展示的順序是有講究的，我建議照系統的分層由下往上走。我們現在完整走一遍，你會看到每一步都在證明一件事。第一步，登入系統——這一步證明 Spring Security 加 JWT 正常運作，登入後直接進 Dashboard 看本月指標。第二步，進入客戶列表，用動態篩選找到 APIM 這家高價值客戶，點進去看詳細資訊——這一步證明 JPA 加 Flyway 的資料層是完整的。第三步，開啟 AI 助理，問它「APIM 最近的合約狀況和商機進度」——你會看到回答用 SSE 一個字一個字串流出來，而且裡面的數字是 Tool Calling 從資料庫查來的真數字，不是編的。第四步，再問「GlobalMart 有流失風險嗎？建議怎麼處理？」——這一步同時展示了 RAG 知識引用跟對話的歷史記憶。第五步，讓 AI 產生行動建議並確認建立待辦任務，把完整的業務閉環走完，最後再開 Swagger UI 秀一下 OpenAPI 文件。這五步，剛好把八章所學各講了一遍故事。還有一個實戰忠告：每個步驟的測試資料都要預先準備好，不要在台上現場打字輸入，現場輸入是 Demo 意外的最大來源。

腳本走順之後，用教材裡的驗證提示詞做最後把關：請 AI 陪你「從零」完整跑一次——啟動服務、登入、瀏覽客戶、跟 AI 對話並確認它查到的數字是真的、看風險與情緒、看儀表板、看團隊分析、再做一次知識庫文件問答，全程沒有錯誤，就算通過結訓驗收。「從零」這兩個字很關鍵，因為 Demo Day 當天你就是從零開機的。

總結這一節：結訓整合不寫新功能，用整合檢查清單逐層排除環境、跨層、資料流三類問題，再用五步展示腳本把作品講成一個完整的故事。下一節，我們來談怎麼用測試策略跟上線檢查清單，讓這套系統不只展示得漂亮，還經得起驗。
